# The API and worker end on a fault with one safe line, and an alarm reads it (2026-10-24)

Date: 2026-10-24

**Implemented (no migration).** Foundation layer 12 (errors and logs). Neither the API nor the worker handled `uncaughtException` or `unhandledRejection` (only the issuer did), so Node's default ran: it prints the error's message and stack to stderr, and a thrown message can carry a value (a patient label, a digest). Both now install a handler first thing in `main.ts` that writes ONE `process-fault` line and exits 1 so ECS replaces the task. The line names the kind and the error class (the API adds a short `code`, such as `ECONNRESET`, when there is one); it never contains the message, the stack or any other property. A second fault while exiting writes nothing more. If the line cannot be written the process still exits.

**Made visible in the same change.** A task that is replaced leaves only a restart behind, so each service gets a log metric filter on `process-fault` and an alarm (`api-process-fault`, `worker-process-fault`: a single occurrence in a minute, silence is normal, audit topic). One fault is a bug, not a blip.

**Tests, written alongside and then proven.** `process-faults.spec.ts` (API) and `process-faults.test.ts` (worker): the line is structured; no message, stack or value is written; a thrown string becomes `non-error`; a free-text `code` is dropped; one line and one exit however many faults; exit even when writing throws. Wiring pins in `main.guard.spec.ts` and `boundaries.test.ts` require the install before anything else runs. Nine deliberate breakages of the new code (message logged, no single-fault guard, an unguarded write, a free-text code kept, the install removed, in both services) each turn a test red. The Terraform guards pin the filter pattern, the single-occurrence threshold and silence handling with weakened-text controls, and run the real handler's output through the filter: the API guard compares the event the handler writes with the filter's pattern, and the worker contract test runs the line through the actual filter pattern and checks it matches no other worker filter.

**Limits.** Not verified in AWS: the alarms firing, and that ECS captures the stderr line in the log group. No test kills a real process: the handlers are exercised with an event emitter. A fault that kills the process before `main.ts` installs the handlers (a failed import) still gets Node's default. The API writes with `fs.writeSync(2, …)` so the line is out before the exit; the worker writes through its logger (stdout), which may be asynchronous on a pipe, so the last line is best effort.
