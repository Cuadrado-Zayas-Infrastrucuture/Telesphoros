# Identical patient-link decisions made at once record one decision (2026-10-25)

Date: 2026-10-25

**Implemented (no migration, no contract change).** Found in the read-only retry check of the ledger write routes (2026-10-25). `insertPatientDecision` already returned the stored decision when the newest one about the same file said the same thing, and answered 200 (`created: false`). But that look-up ran after only a shared lock on the report row (`FOR SHARE`, which callers hold together) and before the ledger lock, so callers that overlapped each read "nothing new" and each inserted. Reproduced with a sleeping trigger that holds the window open: four identical concurrent calls made four rows. An evaluation that relied on the first of them was then built on a decision that was no longer the newest and was refused (`PatientLinkUnverifiedError`). The overlap is what a client that times out and retries while the first request is still running produces.

**The fix.** `pg_advisory_xact_lock(hashtextextended('patient-link:<tenant>:<report>', 0))` as the first statement of the write, before the report row is read, so decisions about one report queue, each look-up sees the previous row, and the repeat is a no-op. The key is used only here, so it cannot join a lock cycle: its holder goes on to take the same shared report-row lock and ledger lock in the order they were already taken, and a waiter holds only shared locks (membership and session rows). Different reports do not wait for each other. The row lock, the ledger lock and the staleness checks are unchanged. `docs/lab-report-reader.md` states that the second of two simultaneous identical requests answers 200.

**Tests, red first.** `patient-link-concurrency.pg-spec.ts` (real PostgreSQL, 4; a trigger sleeping 0.4 s before the insert opens the window every time): four identical simultaneous decisions leave one row, one `created` and three `existing`; an evaluation relying on that decision is accepted afterwards; control: a verified and a rejected decision at once are both recorded; control: decisions about two reports do not wait for each other. The first two failed before the change (four rows). Removing the lock is the old code, which is what failed.

**Limits.** The sleeping trigger is a test device; the real window is the time between the look-up and the ledger lock, which is short. Only this route: the dispute raise still has no retry identity (a retry makes a second open dispute), and corrections and dispute decisions answer a retry with a 409 and no duplicate. Not run against a deployed API or in AWS.
