# The tasks' full ledger walks no longer start together (2026-10-24)

Date: 2026-10-24

**Implemented (no migration).** From the production-readiness audit (items 23 and 32). Every API task ran the full ledger walk the moment it started and again on its own 24-hour timer (jittered 10%), with nothing to space the tasks out: N tasks started by one deploy walked at the same instant and loaded the database N times over, and each timer fired independently.

**What changed.** (1) The walk that follows the check at start begins after a random delay of up to 60 seconds. (2) A task takes a database advisory lock for the length of a full walk (start or timer). Another task finds it taken, retries about every 10 seconds, and after 30 minutes walks anyway. A lock that cannot be asked for is logged and the walk goes ahead. So the lock only delays a check; it never replaces one. `LedgerVerifier.acquirePassLock` holds one of the verifier pool's connections (the pool grows from 2 to 3) and the database frees the lock if that connection closes.

**Why not "one task walks, the others don't" (the audit's wording).** Each task's readiness, its containment view and the "a checkpoint is a shortcut, not a control" rule rest on that task's own full walk; a task that skipped it would have to report `verifying` for ever or claim a verification it did not do. The load problem is the walks overlapping, so they now follow each other instead of being dropped. The daily cost is still N walks per tenant and N checkpoint events per tenant per day; that part of item 32 is not changed and is noted as a decision for later.

**Tests, red first.** `ledger-monitor-pass-lock.spec.ts` (7, fake verifiers sharing one fake lock, fake timers): the walk after start waits a random time up to the jitter; the lock is held for the whole walk and released; two tasks walk one after the other, never together, and both walk; a lock held past the wait limit is walked around, with a log line; a lock that cannot be asked for is walked around; the lock is given back when the walk fails; shutdown while waiting ends without walking. Four deliberate breakages (no jitter, lock never released, a timeout that skips the walk, no lock at all) each turn tests red. `ledger-pass-lock.pg-spec.ts` (3, real PostgreSQL): the lock goes to one verifier at a time and to the next after release; it is free again after the holder's backend is terminated; a holder can still verify.

**Limits.** Not run with many tasks or production-sized chains, and nothing here is verified in AWS. The 60-second jitter and the 30-minute wait are judgements. A walk of a very large ledger by an earlier task can hold the lock up to its per-tenant budgets (15 minutes each); a later task then walks without it after 30 minutes. `docs/ops/ledger-watch.md` has a section on it.
