# Identifier registration can be retried safely (2026-10-24)

Date: 2026-10-24

**Implemented (migration 0040, labelled `breaking`).** From the production-readiness audit (item 25, Medium), second of three creates (patients, identifier registration, invitations). A retry of `POST /patients/:id/identifiers` that had succeeded answered 409 `identifier-in-use`, which the caller could not tell from a number held by someone else. It now follows the report (0014) and patient create pattern.

**Contract.** The body takes an optional UUID `requestId` (lower-cased). The same person repeating the same registration (same patient, system and number) gets the identifier back (201, same id), also after it was withdrawn (its `status` says so). The same id with a different patient, system or number answers 409 with reason `request-id-reused`. The id is per organization and per person. A number held by another patient is refused as before (`identifier-in-use`) and still records the possible-duplicate flag. Without an id nothing changes. The id is never in the response.

**Migration.** Two nullable columns on `patient_identifiers`, a CHECK that the pair is both present (hash a SHA-256 in hex) or both absent, `UNIQUE (tenant_id, created_by, creation_request_id)`, and a trigger that refuses changing a stored identity (the table's existing guard names the columns it protects, so the new ones need their own). A CHECK, a UNIQUE and a trigger on an existing table make it `breaking`: **a release that includes it is a breaking release (an outage window)**; so are 0036, 0037 and the patient create's migration, so it adds no new class. The down refuses while keyed rows exist unless `telesphoros.allow_identifier_retry_drop=yes`. The patient create's migration (0039) is already on `main`, so this one is 0040 (migrations must be contiguous).

**The fingerprint holds no value.** It is the SHA-256 of the patient id, the system and the hex of the keyed digest, which is already the stored form; the number itself still reaches nothing but the digest function. The existing end-to-end check that no row of any table holds the number still passes.

**Races.** A repeat arriving while the first is still being written can meet the number's unique index before the retry id's. After either unique violation the insert rolls back to its savepoint and looks the retry id up: found with the same fingerprint is a replay. A sleeping trigger (test only) makes two repeats both pass the first look-up before either writes; one identifier is stored.

**Tests, red first.** `shared-types` (2): the id is optional, lower-cased, a UUID, other extras refused. `identifier-registration.pg-spec.ts` (real PostgreSQL, 8): 12 simultaneous repeats across two pools store one identifier; the sleeping-trigger race; a replay after withdrawal; a different body refused; separate id spaces per person; another patient's number still refused with the flag; no id behaves as before; the stored identity cannot be changed and the pair CHECK holds. `patient-identifiers.e2e-spec.ts` (3, in memory and on PostgreSQL): the repeat returns the same identifier while one without an id answers 409 and the list holds one; a changed number is refused with the reason and another person has their own id space; a non-UUID is 400. Breakages that turn tests red: no fingerprint comparison, no look-up after a unique violation. (A third, removing the look-up before the insert, changes nothing observable: the look-up after the violation gives the same answer, so that one is an optimisation only.)

**Limits.** The frontend sends no id yet (the field is additive). Retry state is not kept across browser restarts. In the development store the id space is process memory. Not verified in AWS.
