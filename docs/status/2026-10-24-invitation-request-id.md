# Invitations can be retried safely (2026-10-24)

Date: 2026-10-24

**Implemented (migration 0041, labelled `breaking`).** From the production-readiness audit (item 25, Medium), third of three creates (patients, identifier registration, invitations). A retry of `POST /members/invitations` for an invitation that had been made answered 409 `invitation-pending`, which does not say whether the first attempt went through. It now follows the report (0014), patient and identifier pattern.

**Contract.** The body takes an optional UUID `requestId` (lower-cased). The same administrator repeating the same invitation (same address, same roles in any order) gets the invitation back (201, same id), whatever its status is by then (a cancelled or expired one is returned with that status). The same id with a different address or different roles answers 409 with reason `request-id-reused`. The id is per organization and per administrator. A repeat without an id still answers 409 `invitation-pending`. The id is never in the response.

**Migration.** Two nullable columns on `invitations`, a CHECK that the pair is both present (hash a SHA-256 in hex) or both absent, `UNIQUE (tenant_id, created_by, creation_request_id)`, a trigger that refuses changing a stored identity, and a new function `invitation_create_keyed(bytea, text, text[], uuid, text)` (SECURITY DEFINER, `PUBLIC` revoked, executable by the application role). `invitation_create` is untouched, for the images that call it, and the application calls the old function when no id is given. A CHECK, a UNIQUE and a trigger on an existing table make it `breaking`: **a release that includes it is a breaking release (an outage window)**; so are 0036, 0037, 0039 and 0040, so it adds no new class. The down drops the function and refuses while keyed rows exist unless `telesphoros.allow_invitation_retry_drop=yes`. The patient and identifier migrations (0039, 0040) are already on `main`, so this one is 0041 (migrations must be contiguous).

**No race to close.** `member_admin_context()` takes an organization-wide lock for every administrative change, so two repeats cannot interleave: the second sees the first's row, and the function needs no exception handler.

**The fingerprint holds no address.** It is the SHA-256 of the keyed digest of the address (already the stored form) and the sorted set of roles.

**Tests, red first.** `shared-types` (2): the id is optional, lower-cased, a UUID, other extras refused. `invitation-registration.pg-spec.ts` (real PostgreSQL, 6): the repeat returns the same invitation and stores one; another fingerprint refused as `request-id-reused`; ids kept apart per administrator while the address stays unique among pending invitations; only an active administrator may call it; `PUBLIC` cannot; the stored identity cannot be changed and the pair CHECK holds. `members.e2e-spec.ts` (4, in memory and on PostgreSQL): the repeat returns the same invitation while one without an id answers 409 `invitation-pending`; roles in another order are the same request while other roles or another address are refused; a cancelled invitation is replayed with its status and another administrator has their own id space; a non-UUID is 400. Three deliberate breakages (no fingerprint comparison, no per-administrator scope in the SQL, roles not treated as a set in the service) each turn tests red.

**Limits.** The frontend sends no id yet (the field is additive). Retry state is not kept across browser restarts. An invitation made by one administrator cannot be replayed by another. Not verified in AWS.
