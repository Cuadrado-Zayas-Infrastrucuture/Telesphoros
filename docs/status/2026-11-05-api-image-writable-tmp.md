# The API image gives the upload staging folder a writable /tmp

Date: 2026-11-05

Once the intake's multipart listing was fixed (`2026-11-05-intake-multipart-list-permission.md`), the next upload on synthetic staging got one step further and stopped: `POST /reports/:id/upload-attempts` answered 201, then `PUT …/bytes` answered 500 within 70 ms and nothing reached the reports bucket. Report intake stages every upload in a temporary folder made with `mkdtemp` under `os.tmpdir()` (`stage.ts`). The API task runs with a read-only root as user 10001 and mounts its ephemeral `scratch` volume at `/tmp` (`api-compute.tf`). The runtime image is built from `scratch` and had no `/tmp` and no `VOLUME`. The ECS bind-mount documentation says such a volume is root-owned `0755` unless the image declares the path a `VOLUME`, in which case ECS copies the image's contents and permissions onto it. So the folder could not be created and the API answered 500. No check ran the image as its task user with a fresh volume at `/tmp`: the rehearsal's API containers have no `/tmp` mount and never upload.

Reproduced on the image staging runs (`sha256:128206aa…`, read-only root, user 10001, a fresh volume at `/tmp`): `EACCES` on `mkdtemp`, and the same command as root succeeds.

What changed: `runtime-rootfs.cjs` creates `/tmp` with mode `1777` (sticky and world-writable, as `/tmp` is everywhere), and the runtime stage of `api.Dockerfile` declares `VOLUME ["/tmp"]`. Nothing else in the root becomes writable. The guard test requires exactly that one `VOLUME`, in the runtime stage, at the path the API task mounts its scratch volume; a unit test requires the `1777` mode whatever the umask. The rehearsal checks that the image declares only `/tmp` a volume, then runs a new `tmp-smoke.cjs` as user 10001 with a read-only root and a fresh anonymous volume at `/tmp`.

Verification, Node 22.22.0 and Docker Desktop (linux/amd64 under emulation): `test:image` 49 of 49. Three deliberate breaks each turned it red: the `chmod` removed, the sticky bit dropped, the `VOLUME` removed; the files were restored. The new smoke fails on the staging image (`EACCES`) and passes on the rebuilt one, which still refuses writes under `/app` (`EROFS`); the existing runtime smoke passes on the rebuilt image.

Not done: nothing released. The fix reaches staging only with a new image, through a release that also carries everything merged since 767bd0b5, which includes migration 0071 (spec 033 slice 1). Local Docker volumes copy an image's contents without a `VOLUME` too, so the rehearsal cannot show the ECS behaviour itself; the declaration is checked on the image and the upload is checked on staging after the release. The API's error log for an unexpected intake failure carries only `INTERNAL_ERROR`, which is why this took a reproduction to find.
