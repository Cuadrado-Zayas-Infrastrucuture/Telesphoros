# A write to private data now leaves an audit row with the id it touched (2026-10-24)

Date: 2026-10-24

**Implemented (migrations 0037 and 0038).** From the production-readiness audit (item 46, Medium). Every request recorded `api-auth` `accepted`, but that row cannot carry a subject (its CHECK requires `subject_id IS NULL`) and the access-audit interceptor skipped everything but GET, so a patient create, replace or delete left nothing naming what it touched. Now a POST, PUT, PATCH or DELETE on a private route records a `private-write` event (`accepted`) **before the handler runs**, with the controller and handler name and the id in the path when it is a UUID (none for a create), never a body, field, label or value. If the row cannot be stored the handler does not run, the request answers 503 and nothing changes: a write cannot happen unrecorded. Reads are unchanged (recorded after the handler, withheld if the row cannot be stored).

**Migrations.** 0037 widens the `security_audit_kind` CHECK on `security_audit_events` (drop and re-add, as the table's owner role `telesphoros_ledger`) and adds the new one `NOT VALID`, so no request waits on a scan of a table every request writes to; 0038 validates it, which does not block writers. 0037 is labelled `breaking` only because the lint treats any DROP as such: an older image refuses nothing it did before. **Release consequence:** per the release classes, any release that includes 0037 is a `breaking` release (an outage window). 0037's down refuses while private-write rows exist unless `telesphoros.allow_audit_drop=yes` (rows are append-only and are kept; the old CHECK goes back NOT VALID).

**Tests, red first.** `security-audit.interceptor.spec.ts` (8 cases): the event is written before the handler for each of the four methods; the subject is the path id, or null, and a non-UUID id is dropped; the handler does not run when the store throws; nothing for a public route, an unauthenticated request, HEAD or OPTIONS; a read is unchanged (control). `security-audit.pg-spec.ts` (3 new, against real PostgreSQL through the real API): create, replace and delete each leave `api-auth` plus `private-write` with the right route and subject; a write whose row cannot be stored (a CHECK that refuses it) creates nothing and the same request then succeeds; the CHECK allows `private-write` only as `accepted`, refuses `succeeded`, `refused`, `api-auth` `succeeded` and an unknown type, and is validated. Four deliberate breakages (write branch off, handler before the row, CHECK not widened, any outcome allowed) turn tests red; the ordering one crashes the Jest run with an unhandled rejection.

**Limits.** It records the attempt, not the outcome, and not the change: before and after values or changed field names (audit option (b)) are not recorded, pending Compliance's confirmation of the HIPAA audit-control scope. A write refused for role or membership reasons never reaches the interceptor and gets no `private-write` row. Each write now costs one more insert. Not verified in AWS. The audit store is still not anchored outside the database.
