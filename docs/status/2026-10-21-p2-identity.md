# P2 reads its caller from the tenant capability (option B, local)

Date: 2026-10-21

The three application entry points of the inactive synthetic durable workflow (`agentic_synthetic_admit`, `_read`, `_cancel`) took the organization and the person from the session settings `app.current_tenant_id` and `app.current_actor`, which the application login can set to anything (founder decision A, synthetic staging only). Migration `0030_agentic_synthetic_identity` (`-- compat: breaking`) moves them onto the DATA-01 tenant capability. A new helper, `agentic_synthetic_identity()`, is the one place that reads the caller, and it **requires `app.capability` to be set in every binding mode**: `app_tenant()` and `app_actor()` alone fall back to the raw settings in `guc` and `dual`, so a bare swap would have protected nothing. `admit` also refuses, and rolls the whole admission back, unless the queue row `job_enqueue` wrote carries the verified organization and person, because `job_enqueue` still reads the settings itself.

Proof: `apps/backend/test/db/agentic-identity.pg-spec.ts` (runs in the backend PostgreSQL tiers) puts a hostile application login through admit, read and cancel in all three modes, each next to a positive control; `apps/backend/src/db/agentic-identity-migration.spec.ts` (no database) requires the new bodies to equal the 0029 bodies plus exactly the declared edits. Fifteen one-at-a-time defects each turned a test red.

Not changed on purpose: the worker-side `agentic_synthetic_member_current` still writes the tenant setting, so DATA-01 slice 5 (mode `capability`) must not merge before the P2 worker side binds through the internal binding (FR-015) or slice 7. Nothing calls P2 from a route and the API still binds `NullCapabilityIssuer`, so P2 stays unreachable until the API issuer client exists. Local only: nothing is pushed or applied.
