# The intake's multipart listing gets a statement without a prefix condition

Date: 2026-11-05

The first upload ever tried on synthetic staging (release 767bd0b5, 2026-11-05) failed four times out of four: `POST /reports` answered 201, then `POST /reports/:id/upload-attempts` answered 503 within a second. Before it accepts an attempt, the validated intake lists the report's intake prefix twice, object versions and unfinished multipart uploads, and treats a listing it cannot finish as "not empty" (`intake.service.ts`, `upload-inventory.ts`). `iam.tf` allowed both list actions only under `StringLike s3:prefix = reports/*`. The AWS service authorization reference lists `s3:prefix` for `ListBucketVersions` but not for `ListBucketMultipartUploads`: S3 never sends that key for the multipart listing, so the condition never matched, AWS denied the call, and the intake answered 503. The guard test asserted that same shape, which is why no check went red.

What changed: `ReportIntakeInventory` keeps `s3:ListBucketVersions` under the `reports/*` prefix. A new statement, `ReportIntakeMultipartInventory`, grants `s3:ListBucketMultipartUploads` on the reports bucket with no condition. The API still asks only for its report's prefix, and the listing returns keys and upload ids, never bytes. The guard test now requires exactly one statement with the multipart action, with no condition and no other action. Only the API task role carries `app_runtime`, so only the API gains the listing (corrected 2026-11-06: this note first said the worker and issuer roles carry it too; `api-compute.tf` attaches it to the API task role alone, and the live attachments read after the apply agree).

Verification, Node 22.22.0: `guard.test.mjs` 392 of 392. Five deliberate breaks each turned the intake test red: the original shape, a prefix condition put back on the multipart statement, the statement removed, the statement widened with `s3:GetObject`, and the version listing's prefix widened to `*`; `iam.tf` was restored byte-identical. `terraform fmt -check` passes. Ruled out on staging: the bucket policy (it denies only insecure transport, old TLS and the wrong encryption) and the S3 gateway endpoint (allow all). The IAM policy simulator was not usable as evidence: it reports an organization deny for every S3 action of the task role, including the uploads and reads that work.

Not done: nothing applied. The fix reaches staging through an `INFRA` plan and apply under the release claim, after which the upload is tried again. The cause is read from the AWS reference and the code; it was not reproduced by a call made as the task role. The four report records the failed uploads created stay on the synthetic patient: the API has `DELETE /reports/:id`, but no screen offers it yet.
