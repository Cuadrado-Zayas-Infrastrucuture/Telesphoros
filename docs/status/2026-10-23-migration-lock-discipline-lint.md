# The migration lint checks triggers, constraints and lock_timeout (2026-10-23)

Date: 2026-10-23

**Implemented (lint only; no migration, and no existing migration edited).** From the production-readiness audit (items 15 and 16). `migration-lint.ts` said in its own header that it did not look at `ADD CONSTRAINT`, unique indexes or `lock_timeout`, and 0034 shipped labelled `expand` while adding two triggers to live tables with no `lock_timeout`. Two rules now apply from 0028 on (the same boundary as the label), to a table the file does not itself create: an `expand` migration may not add a trigger, a CHECK / FOREIGN KEY / UNIQUE / EXCLUDE / PRIMARY KEY constraint, or a unique index; and any migration that runs `ALTER TABLE`, `CREATE INDEX`, `CREATE`/`DROP TRIGGER` or `CREATE`/`ALTER`/`DROP POLICY` on one must set a non-zero `lock_timeout` first.

**Applied migrations are excused by number, not edited.** `GRANDFATHERED` in `migration-lint.ts` lists 0034 for both rules, with the reason. The spec requires each entry to name a migration that exists, to give a reason, and to be live (without it the migration is reported for exactly those rules), and requires the same text under another number to be reported. Run over every shipped migration with no excuses: of 0028 onwards only 0034 is reported (four findings: a trigger on `patient_merge_decisions` and one on `patients`, each also lacking the setting).

**Corrects the audit.** The audit listed 0033 among the migrations lacking `lock_timeout`. 0033 creates one function and two grants and runs no DDL on a table, so the rule does not apply to it and it passes.

**Not covered.** The lint does not start before 0028, so it does not look at the older migrations. Run unexcused with a label added, these would be reported for the lock rule: 0002, 0003, 0004, 0008, 0010, 0011, 0020 and 0021. 0020 and 0021 are the audit's item-16 concern (`ALTER TABLE ledger_events` drop and re-add of CHECK constraints, with no timeout); they are already applied, cannot be edited, and are not added to `GRANDFATHERED`, which would only hide them in code. DDL inside `EXECUTE` or a `DO` block is not seen (a stated limit with a test). Data rewrites and policy changes on existing tables are still unchecked, as before.

**Tests, written first.** `migration-lint.spec.ts` now has 97 cases, of which these are new: eleven trigger and constraint forms refused under `expand` and accepted under `breaking` and on a table the same file creates; eight DDL forms refused without the setting and accepted with it; the setting must come first, be non-zero and be a statement of its own (not a function's `SET lock_timeout` clause, a comment or a string); dollar-quoted bodies are not read as statements; the excuse list is live and exact. The older fixtures that used bare DDL under a label now carry the setting on the label's line, and one old case that listed `ADD CONSTRAINT ... CHECK` as an accepted additive statement was removed, since it is exactly what the new rule refuses. A breaking migration that ends inside a quote is now reported (it cannot be read for the lock rule) where it used to pass in silence; no shipped migration is affected. Eight deliberate breakages of the new code (either rule off, excuse list emptied or applied to every number, zero value accepted, the statement-start anchor dropped, a later setting counted, bodies not blanked) each turn the spec red.
