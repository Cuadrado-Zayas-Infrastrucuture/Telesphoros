# Infrastructure: a configurable database pool and a connection budget

Date: 2026-10-27

From the 2026-10-27 MVP architecture review. Each API process held up to 10 application connections, fixed in code, and nothing compared the services' connections with what the database accepts: at the largest counts Terraform allowed (10 API tasks, 5 workers, 10 issuers) they could open about 205, more than a `db.t4g.small` instance's default limit allows.

Changed: `DATABASE_POOL_MAX` (1 to 50, default 10, so nothing changes by default) sizes the API's application pool, and Terraform passes it from `api_db_pool_max`. A new `database-connections.tf` adds every pool at its largest count (API tasks x (pool + 3 for the ledger verifier), workers x (WORKER_CONCURRENCY + 3), issuers x 4, and the migration task) and three preconditions on the database instance refuse a plan whose total exceeds `db_connection_budget`. That budget comes from a live `SHOW max_connections` reading; until one exists, a per-class estimate is used, labelled as one: AWS's default for RDS for PostgreSQL is `LEAST({DBInstanceClassMemory/9531392}, 5000)` and `DBInstanceClassMemory` is smaller than the listed memory by an amount AWS does not publish per class, so each estimate is the listed memory's value with a 35% margin, less 5 reserved slots (`db.t4g.micro` 68, `db.t4g.small` 141). Production refuses the estimate, and a class with no estimate needs a reading. `db_connection_demand` reports the total and the budget.

Proved: on real PostgreSQL, the API's application login holds exactly `DATABASE_POOL_MAX` connections under more concurrent work than that (2 and 3; both failed on the fixed pool, which opened 5 and 6); the loader's default, bounds and refusals; a text guard keeps the Terraform pool numbers equal to the code that opens the pools, the estimates equal to the stated formula, and the refusals present, each rule seen to fail. New offline plan runs in `profiles.tftest.hcl` cover the sum, the refusal above the budget, the labelled estimate, production's refusal of an estimate and an unlisted class; they need the pinned Terraform and its providers, so they first run in CI. Not changed: the database parameter group, any AWS resource, the worker and issuer pool sizes. Not verified: any live `max_connections` value. The existing `database_connections_high` alarm fires above 80 connections, which is above the `db.t4g.micro` estimate; it is left as it is.
