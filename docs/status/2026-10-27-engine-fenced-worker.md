# Feature: a fenced evaluation-request worker (H3, local)

Date: 2026-10-27

H3 of the engine harness sequence, after H1 (durable admission, PR 80) and H2 (a cancellable read, PR 81). H1 stored evaluation requests and their queue jobs, with a completion table no one could write. This change adds the consumer that answers them, and the database check that makes its answer safe under at-least-once delivery.

Changed: migration 0051 adds `evaluation_job_fence(job, worker)`, a narrow definer function owned by the queue's owner role, which share-locks the request's job while the caller holds it and refuses otherwise (EJ001). It also adds a check on `evaluation_request_completions` that accepts a completion only from the worker holding the job, for the person who asked while they may still write, and only for an evaluation of exactly what the request named under its pinned profile (report, capture, accepted decision, patient, text, recordings, base knowledge set). `PostgresLedgerRecordsRepository.insertEvaluation` takes an optional completion and stores the evaluation and its completion in one transaction, after fencing first. `EvaluationRequestConsumer` reads the request (fenced, so a worker whose lease ran out learns it before reading), reports an already-completed request as done without reading again, refuses a request pinned to another execution profile, and otherwise calls the same `EvaluationsService.create` as the API, with the job's abort signal (H2). The job runner and its logger moved from `apps/worker` into `@telesphoros/jobs` unchanged, so the backend can use them without importing the worker app. `src/evaluation-worker.ts` is a separate backend entry point (`start:evaluation-worker`), refused unless `EVALUATION_WORKER=enabled`, the lab-report pipeline is enabled, a separate queue login is given, and the configured profile matches the knowledge set and recordings the process loaded.

Proved on real PostgreSQL (migrations, roles, row-level security, the real queue functions, ledger and storage) with public fixture D01, each check failing when its guard is removed (nine mutations, all caught): the held worker stores one evaluation and one completion, and the request reads as completed; a worker whose lease was lost before it started is refused without reading, and the new holder completes; a lease lost or run out during the read stores nothing; while a storing transaction holds the job, an expired lease cannot be claimed by another worker; a requester who loses access during the read leaves neither the evaluation nor the completion; a redelivered job completes without a second read or evaluation; a mismatched profile is refused without reading; an aborted job stores nothing; the shared runner claims, evaluates, completes and succeeds the job. Direct inserts are refused for a worker not holding the job, an evaluation of another report, and another organization. Reverting 0051 refuses while a completion exists, as the restricted migrator login. H1's status read now compares the base knowledge set of a dispute-overlay evaluation with the pinned profile, as 0051 does; before, a request completed while a dispute was active read as unavailable (the new test failed on the old read). A different knowledge set without an overlay is still refused.

Not changed: no route, schedule, outbox route or production consumer (`PRODUCTION_JOBS` and the worker app's registrations are unchanged); no deployment or infrastructure file names the new entry point (a test checks this); no model, provider or inference adapter; clinical rules, holds and the D01 to D12 goldens. The lab-report pipeline, and so this worker, stay refused in production. The new worker acts for the requesting person through the tenant binding the tests use; capability-mode binding for a background worker is not designed yet. The entry point was built and its start-up refusals tested, but it was not run as a process against a full configuration. The goldens and the real-engine specs need the engine, which is not in the public checkout: they were skipped (ENGINE ABSENT).
