# The upload's request id now reaches its stored-file check (2026-10-24)

Date: 2026-10-24

**Implemented (migration 0042, labelled `breaking`).** Second half of audit item 50 ("a job cannot be traced to its request"); the first half (the stored-file check payload and the worker's log line accept an optional `requestId`) is already on `main`. The upload commit now passes the request's id to the outbox event it writes in its own transaction, the relay copies it into the job payload, and the worker's `file-verified` line shows it, so a stored-file check can be matched to the upload request that caused it.

**What changed.** Migration 0042: a nullable `outbox_events.request_id` (no CHECK); a per-route `outbox_routes.carry_request_id` (default false, true for `report.file-committed`); a three-argument `outbox_append(text, uuid, text)` (the two-argument form is kept, for images that call it) that keeps only an id of the shape the jobs table accepts for a payload string (letters, digits and hyphens, 1 to 64) and stores nothing otherwise; `outbox_relay` copies the id into the payload for an opted-in route; the event guard trigger also refuses changing `request_id`. The API change is one line: `commitAttempt` passes `currentRequestId() ?? null`. Why an id with a dot or underscore is dropped rather than failing: the `X-Request-Id` header may carry one (the API accepts `[A-Za-z0-9._-]{8,64}`), and the jobs table's payload CHECK would refuse it, leaving a poison event.

**Release class.** Two `CREATE OR REPLACE` function bodies make it `breaking` under the migration lint, as 0036 was: an older worker would get a payload key its schema refuses, so the worker that accepts `requestId` (already on `main`) must run first. **A release that includes 0042 is a breaking release (an outage window)**; so are 0036, 0037 and 0039 to 0041, so it adds no new class. The down restores the 0036 relay and the 0024 guard and drops the objects; unlike the retry-identity rollbacks it does not refuse when ids are stored, because the loss is traceability, not behaviour.

**Tests, red first.** `outbox-request-id.pg-spec.ts` (real PostgreSQL, 8): a commit inside a request stores its id on the event and the job payload gets `{reportId, requestId}`; a commit with no request carries none and the job is as before; an id with a dot or underscore is dropped and the event is relayed (not stuck); the id travels only on an opted-in route (control: switched off, then on); the two-argument `outbox_append` still works and the new form needs the organization binding; the new function is executable by the application role only (not PUBLIC, not the worker); an id of the wrong shape becomes none; the stored id cannot be edited, even by the owner. All eight failed before the migration. Three deliberate breakages (the relay ignoring the route flag, no shape filter, the API sending no id) each turn tests red. One catalog-pinning list changed (`tenant-capability.pg-spec.ts`: the new three-argument function is one a revert of 0031 removes); no constraint or CHECK was added, so the constraint lists did not.

**Limits.** Only the stored-file check job has a request behind it (`files.verify-stale` and the upload sweep are scheduled). The id is traceability, not authorization or audit: it is whatever the caller supplied if it passes the shape check. Not run against a deployed worker or in AWS.
