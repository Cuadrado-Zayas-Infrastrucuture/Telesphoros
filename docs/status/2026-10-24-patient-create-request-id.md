# POST /patients can be retried safely (2026-10-24)

Date: 2026-10-24

**Implemented (migration 0039, labelled `breaking`).** From the production-readiness audit (item 25, Medium), first of three creates (patients, then identifier registration, then invitations). A retry of a `POST /patients` that had succeeded answered 409 (the label exists); a clinician who then changed the label made a second record for one person. Reports already had an optional `requestId` (0014); patients now follow the same pattern.

**Contract.** `POST /api/v1/patients` accepts an optional UUID `requestId` (`patientCreateSchema` in shared types; lower-cased). With it, the same person repeating the same label gets the original patient back (201, same id), even if the label has since been edited and even though a repeat without an id would meet the label and answer 409. The same id with a different label answers 409 with reason `request-id-reused`; so does the id of a patient that has since been deleted. The id is per organization and per person. Without an id nothing changes. `PUT` takes no id, and the id and its fingerprint are never in the response.

**Migration 0039.** Two nullable columns on `patients` (`creation_request_id`, `creation_request_hash`), a CHECK that the pair is both present (hash a SHA-256 in hex) or both absent, `UNIQUE (tenant_id, created_by, creation_request_id)`, and a trigger that refuses changing a stored identity. Legacy rows are untouched. A CHECK, a UNIQUE and a trigger on an existing table make it `breaking` under the migration lint: **a release that includes it is a breaking release (an outage window)**. This is the third breaking migration in the unreleased set (0036, 0037, now 0039), so it adds no new class of release. The down refuses while keyed rows exist unless `telesphoros.allow_patient_retry_drop=yes`.

**How a repeat meets the label.** The service looks the request id up first; a stored patient with the same fingerprint is returned and the label check is skipped. Otherwise the label is checked, then `insertOrReplay` stores the row with `ON CONFLICT DO NOTHING` (no conflict target, because a concurrent repeat can meet the label's unique index before the request id's) and, when nothing was stored, reads the row under this request id: found with the same fingerprint is a replay; missing, or a different fingerprint, or deleted, is refused as `IntegrityError` (409). The development store behaves the same.

**Tests, red first.** `shared-types`: the schema takes the id (lower-cased), refuses a non-UUID and other extra keys, and the `PUT` body still refuses an id. `patient-registration.pg-spec.ts` (real PostgreSQL, 9): 16 simultaneous repeats across two pools store one patient; a replay after a label edit; a different body refused; ids kept apart per person; a deleted patient's id refused; a label another patient holds still refused; lookup by id is per person and organization; the stored identity cannot be changed and the pair CHECK holds; a patient without an id is as before. `patients.e2e-spec.ts` (3): the repeat returns the same patient while a repeat without an id answers 409 and the list holds one; changed label refused with the reason, another organization's id space is separate; a non-UUID is 400 and `PUT` refuses an id. Four deliberate breakages (no fingerprint comparison, no deleted check, no look-up before the label check, no reuse refusal) each turn a test red.

**Limits.** Retry state is not kept across browser restarts, and nothing in the frontend sends an id yet (the field is additive). The fingerprint covers the label only, because the label is the only input. The migration number (0039) is the next free one on `main` at the time; branches that add migrations must be merged in number order or renumbered. Not verified in AWS.
