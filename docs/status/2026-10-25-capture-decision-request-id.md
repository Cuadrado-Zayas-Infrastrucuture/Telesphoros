# A retried capture decision no longer makes a second acceptance (2026-10-25)

Date: 2026-10-25

**Implemented (migration 0044, labelled `breaking`).** Inherited audit item 1. `POST /captures/:id/decision` inserted a new acceptance row on every call. Evaluations and corrections are checked against the newest acceptance of the capture, so a reviewer whose "accept" went through but whose answer was lost, and who repeated it after an evaluation existed, left that evaluation built on an older decision: reads showed it as not current and a correction on it failed `StaleAcceptanceError`.

**What changed.** Same cure as the report, patient, identifier and invitation creates. Migration 0044 adds `creation_request_id` and `creation_request_hash` to `capture_acceptances`, a pair CHECK (both or neither, the hash 64 hex) and `UNIQUE (tenant_id, created_by, creation_request_id)`. `decisionCreateSchema` takes an optional `requestId` (UUID, lower-cased). The service fingerprints the capture, the decision and the note (never anything else); the repository takes an advisory lock on (organization, reviewer, id), looks the id up, and either returns the stored decision (`created: false`, nothing written, no second note) or writes the new one with its identity. The same id with another fingerprint raises `CaptureDecisionRequestReusedError`, answered 409 `request-id-reused`. A request without an id behaves exactly as before. No guard trigger: the table already refuses every update. The ledger's projection of a decision lists its columns, so neither new column reaches an event hash (tested: a keyed and an unkeyed decision project the same fields).

**Release class.** A CHECK and a UNIQUE on an existing table make it `breaking` under the lint, as 0039 to 0041 were; it adds no new class to the unreleased set. An older image does not send the id and refuses nothing it did before. The down refuses while any retry identity is stored unless `telesphoros.allow_capture_decision_retry_drop=yes`, and lifts `FORCE ROW LEVEL SECURITY` for that check (the migrator sees no rows under it otherwise; see the 2026-10-24 down-guards note).

**Tests, red first.** `capture-decision-request.pg-spec.ts` (real PostgreSQL, 8): replay returns the stored decision and writes nothing (one row, one note, two ledger events); accept, evaluate, repeat: the evaluation is still current; control: a repeat without an id is a new decision and leaves the evaluation on the older one; another decision, note or capture under the same id is refused and leaves no note; the id is per reviewer and per organization; five concurrent repeats leave one decision, one note and one event; the projection is unchanged; the table refuses an id without a fingerprint, a bad fingerprint, a duplicate and any update. Five of them failed before the change. `captures.decide.spec.ts` (4): the fingerprint changes with the capture, decision and note and not otherwise, no identity is sent without an id, and the 409. `shared-types` (2). The migrator-login down test gained the 0044 case (written through the application login). Pins updated: `schema-acceptance.ts` (the unique key and the CHECK name).

**A test of #45 made independent of what comes after it.** `drop-recommendations.pg-spec.ts` assumed its migration (0043) is the last: its restricted-owner test ran a full `migrateUp`, which now also applies 0044 and fails because that owner does not own `capture_acceptances`, and its revert test undid "the last migration", which is now 0044. It now applies only the migrations up to the drop in the first case and reverts the drop and whatever sits above it in the second, so a later migration cannot break it. No behaviour of the drop changed.

**Limits.** Only this endpoint: the other decision routes (patient link, corrections, dispute decisions) were not checked for the same retry problem; merge decisions already have one decision per proposal. A client must send the id to be protected: no frontend calls this route yet. The id is not authorization or audit. Not run against a deployed API or in AWS.
