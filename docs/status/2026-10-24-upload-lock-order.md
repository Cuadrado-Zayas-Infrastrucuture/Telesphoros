# A declaration and a commit for the same report no longer deadlock (2026-10-24)

Date: 2026-10-24

**Implemented (no migration).** From the production-readiness audit (item 2, Medium), first recorded as reasoned, now **reproduced**. `declareAttempt` took the run row (`report_upload_runs`) and then the report row; `commitAttempt` took the report row, then the attempt row, then the run row. The same two rows in opposite orders: a declaration and a commit for the same report could each hold one and wait for the other, and PostgreSQL ended one with `40P01 deadlock detected`. Nothing retried it. In real use the window is microseconds and needs both calls on one report at once (a retry or double-click declaring again while the first attempt is committing); the audit's severity stands.

**The fix.** `declareAttempt` now locks the report row (`SELECT 1 … FOR UPDATE`) right after its advisory lock and before it touches the run row, so every transaction that holds a run row already holds its own report row. Checked against every statement that touches `report_upload_runs`: commit (report, attempt, run), cleanup finish (attempt, run) and reconciliation (run only) agree with it. And `declareAttempt` and `commitAttempt`, both safe to repeat (a declaration by its request id, a commit by its attempt state), run their whole transaction once more after `40P01` or `40001`, through `retryOnConflict`; no other error is retried and a second conflict is the caller's. Nothing else was changed.

**Tests, red first, against real PostgreSQL.** `upload-lock-order.pg-spec.ts` uses the real repository calls and a synthetic trigger that sleeps while the run row is held (never part of a deployment) to open the window every time. On the old code the overlap raised `error: deadlock detected`; now both calls finish, and the end state is consistent (exactly one of the new declaration and the commit wins, and the reserved bytes match). The overlap tests run with the retry switched off, so they prove the order and not the retry: a first version let the retry rescue the deadlock and a deliberate removal of the new lock did not turn it red, which is why. With it switched off, removing the lock turns the tests red. The retry has its own spec (`40P01` and `40001` once, nothing else, a second conflict propagates) and two integration cases (repeat after one conflict and succeed; give up after one retry; a unique violation is not retried). Three deliberate breakages (the lock removed, the retry removed, the retry applied to every error) are each caught; the lock one only after the overlap tests were changed to run without the retry.

**Limits.** The trigger is a test device: the real timing was not observed. Other lock-order pairs in the repository (tenancy, membership, ledger) were not audited here. Retrying `commitAttempt` after a conflict repeats its outbox event inside the same rolled-back transaction, so nothing is duplicated. The retry is not applied to other writes; each needs its own check that it is safe to repeat.
