# ECS task commands no longer repeat the image ENTRYPOINT (local)

Date: 2026-10-21

The API image (`infrastructure/docker/api.Dockerfile`) sets `ENTRYPOINT ["node"]` and `CMD ["dist/main.js"]`. An ECS container-definition `command` replaces only the `CMD`, so a command that starts with `node` runs `node node ...` and dies with `Cannot find module '/app/node'`. Three task definitions and the staging run-task script were written that way, and nothing had failed only because none of it has been applied. `worker.tf` now runs `["worker/main.js"]`, and `api-compute.tf` runs `["dist/db/cli.js", "migrate", "up"]` and `["dist/db/cli.js", "provision-logins"]`, as `issuer.tf` already did. `scripts/staging/run-task.sh` builds the same kind of container override for `aws ecs run-task` and had the same leading `node`; it is fixed too (found while running the tests, not in the original list). Health checks (`["CMD", "node", "-e", ...]`) are untouched: ECS runs them directly, not through the ENTRYPOINT.

A new guard, `infrastructure/terraform/entrypoint.guard.test.mjs` (run by `pnpm test:infra`), reads the Dockerfile's ENTRYPOINT and fails if any container that runs `var.api_image` or `var.api_migrate_image` has a `command` starting with it, or if the run-task override does. It has a floor (it fails if it finds fewer than four task commands) and weakened-copy controls (each of the four tasks and the override with `node` put back, a new file, a shell-form or missing ENTRYPOINT, an empty scan), and it is shown not to flag a nested health check or another image. The four older guards that pinned the old text were updated with it.

Checked with `docker run --network none` on an image built from the Dockerfile: `worker/main.js` starts and stops at `worker failed to start: Worker settings are invalid: DATABASE_URL`; `node worker/main.js` fails with the module-not-found error; `dist/db/cli.js migrate up` and `dist/db/cli.js provision-logins` reach their own missing-configuration messages. Not verified: ECS itself, the x86 Fargate image, and a real database. The image rehearsal (`infrastructure/docker/rehearsal-driver.cjs`) still starts the worker with `spawn(process.execPath, ['worker/main.js'])` from inside the container, so it bypasses the ENTRYPOINT and could not have caught this; that is a follow-up.

Local only: nothing is pushed, nothing applied in AWS.
