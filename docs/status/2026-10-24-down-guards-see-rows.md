# Down-migration guards now see the rows when the migrator runs them (2026-10-24)

Date: 2026-10-24

**Implemented (no new migration; five down files edited).** Found while re-checking the inherited audit items (item 7). The "refuse to drop populated data" guards in the down migrations ask `EXISTS (SELECT 1 FROM <table> ...)`. The login an operator uses for `migrate down`, `telesphoros_migrator`, owns the tables but is not a superuser and has no `BYPASSRLS`, and four of the guarded tables have `FORCE ROW LEVEL SECURITY` with policies only for other roles, so that login saw no rows: the guard answered "empty" and the down dropped populated data without the refusal. Every existing down test ran as the cluster superuser, which sees every row, so none noticed.

**Which guards were blind (reproduced as the migrator, all five red before the change):** 0010 (report evidence, on `reports`), 0014 (report retry identities, on `reports`), 0015 (upload attempts, on `report_upload_attempts`), 0039 (patient retry identities, on `patients`), 0040 (identifier retry identities, on `patient_identifiers`). The others were already safe: 0016, 0023, 0024, 0028 and 0029 switch to the owning role before they look; 0017, 0018, 0019, 0022 and 0041 read tables that are not forced (the owner sees them) or have no row-level security; 0042 deliberately has no guard.

**What changed.** In each of the five files the guard is preceded by `ALTER TABLE <table> NO FORCE ROW LEVEL SECURITY` (the owner may) and, for the three tables that survive the down, followed by `FORCE ROW LEVEL SECURITY` again, all in the migration's own transaction, so a refusal rolls the change back with everything else. 0015 drops the table afterwards and does not restore it. 0010, 0014 and 0015 also gained `SET LOCAL lock_timeout = '2s'` (0014, 0039 and 0040 already had it). No role, grant or attribute changed; the migrator is still not a superuser and still has no `BYPASSRLS`. `docs/database.md` no longer says the table owner bypasses row-level security.

**Pinned history changed on purpose (your decision, 2026-10-24).** The migration-history pin covers 0010, 0014 and 0015 by checksum of up and down together, so editing their downs changed three checksums; `test/migration-history.spec.ts` carries the new values in this PR. A database that already applied the old 0010, 0014 or 0015 will refuse to migrate (checksum mismatch) until it is recreated; nothing is deployed, so this concerns only local and rehearsal databases. 0039 and 0040 are not pinned. Once a release exists this route is closed: a fix to an old down would then need a runner-level change.

**Tests.** `test/db/down-guards-as-migrator.pg-spec.ts` (real PostgreSQL, 6): it provisions the real logins with `provisionLogins`, migrates up as `telesphoros_migrator`, fills the guarded table as the admin, reverts everything above the migration under test with the audit setting on, switches it off, and expects the one migration to be refused with its own message, the refusal to leave the version applied and the tables forced, the opt-in setting to let it through, and `FORCE` to be on again afterwards; plus a control that the same rollback with the tables empty goes through. All five populated cases failed before the change. One deliberate break (dropping the `FORCE` restore in 0039) turns five tests red.

**Limits.** The 0029 guard (it switches to `telesphoros_jobs`, whose policies are `USING (true)`) is reasoned from the policy definitions, not run populated. Nothing here was run through the `db migrate down` CLI itself, only through `migrateDown` with the same login. Editing applied down files is only safe because nothing is deployed; once a release exists, a later fix to an old down must be a new migration's job. Whether an RDS migrator login behaves like the one `provision-logins` creates is not checked (AWS wiring is deferred).
