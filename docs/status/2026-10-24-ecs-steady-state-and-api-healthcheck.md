# A failed deploy fails the apply, and a wedged API process is replaced (2026-10-24)

Date: 2026-10-24

**Implemented (no migration; Terraform text only).** Foundation layers 5, 6 and 11. (1) `wait_for_steady_state = true` on the API, worker and issuer ECS services: without it `terraform apply` returned as soon as the service was updated, so a deployment the circuit breaker then rolled back still read as a success. (2) A container `healthCheck` on the API task: `node -e` asks `https://127.0.0.1:3000/api/v1/health` every 30 seconds (5 second timeout, 3 retries, 60 second start period), so a process whose event loop no longer answers is replaced by ECS. It asks the liveness route, which touches no dependency, so a database slowdown cannot restart healthy tasks (the load balancer keeps asking `/ready`). The worker and the issuer already had the same kind of check on `/livez`.

**The check was run, not just read.** The command as written in Terraform is taken out of the text and executed by the guard against a throwaway HTTPS server with a self-signed certificate (made with `openssl` at test time; no key is committed): a 200 passes, a 503 fails, nothing listening fails. Two controls prove the pieces matter: without `NODE_TLS_REJECT_UNAUTHORIZED='0'` the self-signed listener is refused and the check fails; a path the server does not answer fails. The listener is always TLS in production (the certificate and key are injected into every service task), and the load balancer does not verify that certificate either, so the loopback request does not.

**Tests.** `api-compute.guard.test.mjs`: the steady-state rule, the container check's path (`/api/v1/health`, never `/ready`), timings, scheme and certificate setting, the executed-command test, and four weakened-text controls (service stops waiting, checked on `/ready`, plain HTTP, one retry). `worker.guard.test.mjs` and `issuer.guard.test.mjs` each pin the steady-state rule with a control. `tofu fmt` is clean; CI's `terraform` job runs `validate` and `terraform test`.

**Limits.** Not verified in AWS: ECS acting on the check, the 60 second start period being enough (it is a judgement, not a measurement; the API's start includes a ledger check of up to 20 seconds), and `terraform apply` waiting the way the provider documents. A failed wait leaves the apply failing after the rollback, which the runbook now says. The check needs `node` in the image, as the worker's does; no image exists yet to confirm it. No autoscaling and no RDS alarms here: those are separate items (the autoscaling targets need your decision).
