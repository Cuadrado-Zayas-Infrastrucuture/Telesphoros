# Infrastructure: the connection budget counts the deploy peak, and the connections alarm follows the budget

Date: 2026-10-27

A gap in the connection budget (`2026-10-27-database-connection-budget.md`). The sum counted each service at its usual number of tasks, but the API, worker and issuer services all deploy with `deployment_maximum_percent = 200`: new tasks start before the old ones stop, so for a few minutes there are twice as many. At the largest counts Terraform allows that is about 409 connections, not 205. Separately, `database_connections_high` fired above a fixed 80 connections, above the `db.t4g.micro` estimate of 68, so on that class it could never fire before the limit was reached.

Changed: `database-connections.tf` counts the three services at `connection_deploy_peak_percent` (200) of their counts, the migration task once (it runs before the deploy); the plan refuses a deploy peak above the budget as it refused the usual count. The alarm's threshold is 80% of `local.connection_budget`: the reading once `db_connection_budget` is set, the class estimate until then (54 on `db.t4g.micro`, 112 on `db.t4g.small`). At the default counts the deploy peak is 41 connections on a synthetic plan and 49 with the issuer.

Proved: the connection guard requires each service's `deployment_maximum_percent` to equal `connection_deploy_peak_percent` and the sum to use it; the alarm guard requires the budget-derived threshold. Each new rule was seen to fail (a service's percent changed, the multiplication removed, the threshold set back to 80 or to the whole budget). `profiles.tftest.hcl` updates the two sums to the deploy peak, asserts the thresholds (80 for a budget of 100, 54 on the micro estimate), and adds a run whose usual count fits the budget and whose deploy peak does not. Those plan runs need the pinned Terraform and its providers, so they first run in CI. Not changed: the deploy percentages, the estimates, the pool sizes, autoscaling, any AWS resource. Not verified: any live `max_connections` value.
