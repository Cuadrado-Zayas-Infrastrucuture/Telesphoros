# The API drains before it closes the database pool (2026-10-24)

Date: 2026-10-24

**Implemented (no migration).** From the production-readiness audit (item 48, Medium). Read from the installed Nest 12.2.0 (`nest-application-context.js`): `close()` runs `onModuleDestroy`, then `beforeApplicationShutdown`, then closes the HTTP server, then `onApplicationShutdown`. The API ended its database pool in `onModuleDestroy`, so a request still running when SIGTERM arrived lost its pool under it, and a connection arriving in the gap met a closing listener. There was no drain cap and no pause: ECS sent SIGKILL after 30 seconds.

`installGracefulShutdown` (`common/graceful-shutdown.ts`) replaces `app.enableShutdownHooks()` in `main.ts`. On SIGTERM or SIGINT it waits 5 seconds, stops accepting and lets requests in flight finish for up to 20 seconds (then cuts what is left), then calls `app.close()` (which ends the pool) and exits 0. A 29-second deadline exits 1 if the close hangs. A second signal is ignored. The same drain-then-close order and cap as the issuer's.

**Tests, red first.** `graceful-shutdown.spec.ts` (7, against a real Nest app and a real listener): a control that reproduces the old behaviour (`app.close()` alone: the request in flight answers 500 because the pool is gone); the new path lets that request finish (200) and ends the pool only after it; a request arriving during the pause is still served, then the listener is gone; a request that outlasts the cap is cut and the close still completes; a second signal is ignored; the deadline exits 1 when the close hangs; the log lines carry only their fixed fields. Five deliberate breakages (no drain, no pause, no cap, no deadline, no single-shutdown guard) each turn tests red. `main.guard.spec.ts` pins the wiring; `api-compute.guard.test.mjs` reads the constants and the container's `stopTimeout` and requires pause + drain + margin to end at least 2 seconds before it (five weakened-text controls).

**Limits.** Not verified in AWS: how long the load balancer keeps sending to a task that ECS is stopping, so the 5-second pause is a judgement, and ECS's sequencing of deregistration and SIGTERM. An upload longer than the cap is cut, as before. The worker's stop was already bounded (PR #6). `db/cleanup.ts` still calls `process.exit(143)` on SIGTERM if the API ever calls `makeTempDir`; it does not today (audit note, unchanged). The issuer keeps its own drain helper.
