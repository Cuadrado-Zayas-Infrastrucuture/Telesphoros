# A timed-out fixture build can no longer keep Jest alive after the summary (local)

Date: 2026-10-21

Two hosted runs (39046806543 on 2026-10-17, 39370538229 on 2026-10-20) printed the Jest summary and then idled until the 30-minute run deadline, which spent the shared budget and made the next job's deadline arming fail. The cause is that Jest does not cancel the async work a timed-out hook or test abandons. A spec that built its application or database in `beforeEach` lost its only reference to the half-built fixture; the build finished later, the application started listening, and nothing closed it. The tier runs Jest in one process (`maxWorkers: 1` with `TEST_DATABASE_URL`), so that listener and its PostgreSQL sockets kept the process alive. Only two specs (`local-storage-intake`, `report-registration`) held their pending fixtures; at least 84 of the 91 specs that use the helpers did not, including `local-storage-cleanup` and `readiness`, the failing ones of the second run.

`createTestApp` and `createEphemeralDatabase` now register every build in flight and every fixture they hand out (`test/helpers/fixture-registry.ts`). The test environment (`test/helpers/fixture-environment.cjs`, set in `jest.config.js`) drains them when a test file ends, after the spec's own `afterAll` and before Jest tears the module registry down: it cancels unfinished builds, waits for their own unwinding to drop what they created, then closes whatever no owner closed. It prints one `[fixture-drain]` line naming the file when it had anything to reclaim, and stays silent otherwise. No spec, deadline or production file changed, and nothing is forced to exit. `JEST_HANDLE_REPORT=1` prints what still holds the process after the run (`--detectOpenHandles` cannot: Jest skips TCP and TLS client sockets).

Reproduced before the change, with induced timeouts, on macOS and in a Linux container: `local-storage-faults`, `readiness` and `local-storage-cleanup` hang after the summary; with the change they exit by themselves and leave no database. A spec that leaks a connected `pg` client on its own still hangs, as it should. `scripts/test-fixtures/lifecycle.test.cjs` gained three controls that fail if the drain is removed or weakened, and two that show the unprotected children going wrong without it. Not covered: a client a spec creates directly with `new Client` or `new Pool`, and a build that never settles (the drain waits 20 s, then goes on).

Local only: nothing is pushed.
