# Feature: queue an evaluation and read its status over HTTP, behind a flag (H4 slice 1, local)

Date: 2026-10-27

Slice 1 of [spec 006](../../specs/006-async-evaluation/spec.md) (H4), approved by the founder on 2026-10-27 with D1 to D5 as recommended. H1 (PR 80) stored evaluation requests and their queue jobs, and H3 (PR 82) added the worker that answers them; neither was reachable from the API.

Changed: a new setting `EVALUATION_REQUESTS` (`disabled` by default) opens two routes, `POST /reports/:id/evaluation-requests` (H1's admission: 202 for a new request, 200 for an identical replay, 409 `idempotency-conflict` for a changed one; roles `clinician` and `reviewer`, rate class `expensive`) and `GET /evaluation-requests/:id` (H1's status; clinical-read roles; 404 for another organization). Configuration refuses `enabled` in production, without `LAB_REPORT_PIPELINE=enabled`, and without a valid `EVALUATION_EXECUTION_PROFILE` (never echoing it). The API builds the admission service only while the switch is on, after checking that the profile names the knowledge set and recordings it loaded, as the worker does. Switched off, both routes answer 503 `EVALUATION_REQUESTS_DISABLED` (a new error code) after authentication and roles and before the body is read. The H1 boundary test is rewritten on purpose (founder decision D1): only the lab-reports module and the new controller may name the admission service, and no module or controller may name the H3 consumer or its entry point; its checks on `src/main.ts`, `PRODUCTION_JOBS`, the worker app, `infrastructure/` and `.github/workflows/` are unchanged.

Proved on real PostgreSQL with public fixture D01 (`test/evaluation-requests-api.e2e-spec.ts`), and in `env.spec.ts`: an identical replay returns the same request and no second job; the same retry identity for another capture is refused (409) with nothing queued; a reader is refused (403) and a reviewer admitted (control); a reader can read a request, another organization gets 404 and a malformed id 400; a body carrying a provider, a profile or a report id is refused (400); D01 reads as completed once the H3 consumer answers it, and the evaluation it names can be read; switched off, the admission service does not exist, both routes answer 503 (an invalid body too, so the gate runs before validation) and still 401 and 403 first; the API refuses to start when the profile names a knowledge set or recordings it did not load. Eleven mutations were each caught: the production refusal, the pipeline requirement and the profile check in configuration; the gate guard; the roles on admission (by the route inventory); the start-up profile check; the service built while off (caught because the app then fails to start, not by the absence check); and four boundary breaks (the consumer in `src/main.ts`, in `PRODUCTION_JOBS`, the worker named in an infrastructure file, the service named by another module). The verification record is [docs/verification/evaluation-requests-api.md](../verification/evaluation-requests-api.md).

Not changed: the H3 worker and how it acts for the requesting person (capability mode for a background worker is a separate founder decision, needed before any real data); `PRODUCTION_JOBS`, the worker app, schedules, outbox routes, infrastructure and CI workflows; the synchronous evaluation route; clinical rules, holds and the D01 to D12 goldens; any model or provider. Cancel (slice 2) and the local review page (slice 3) are not in this change. The engine-only specs were skipped (ENGINE ABSENT), as in every public run.

Local only until the founder says push.
