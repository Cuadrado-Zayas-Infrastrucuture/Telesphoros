# A stored structured revision can be assessed, synthetically (032 S3, PR 2b)

Date: 2026-11-03

`EvaluationsService.storeStructured` assesses the stored structured revision of a report against a synthetic knowledge set and stores the result as an evaluation that rests on that revision (the source kind migration 0070 added). No route, job or page calls it yet, so staging looks the same after this merges; it cannot store an assessment there until the synthetic-staging profile names the data origin (PR 3). Nothing is a clinical release: every record carries `synthetic` and `clinicalUse: not-approved`.

What it does: it reads the same reconciliation the review screen shows, and assesses only a revision that is open for review, with every finding accepted as evidence by a second person and each one a tested, resolved, interpretable diplotype. The engine's own mapping turns the diplotype into a phenotype; the laboratory's phenotype is never used. Anything unreviewed, held, rejected, uncertain, not a diplotype, an extra copy number, from a preliminary report or an unprovided assay, or in conflict with another stored source is held: stored with no result and fixed wording, naming codes and finding ids only. Stale evidence, a revision that is not the one under review, no stored revision, no verified patient link, a report that is not structured, an origin that cannot be named and a missing build version are refused and store nothing. Disputes are applied as on the PDF path.

What changed: `evaluations.service.ts` (`storeStructured`, with the cell-provenance and dispute-overlay steps shared with the PDF path), `structured-assessment.ts` (the pure plan), `structured-hold-codes.ts` (wording), `structured-reconciliation.ts` (the reconciliation moved out of the records service unchanged), `StructuredRevisionsRepository.readForReport`, the mapper's hold wording, a second synthetic knowledge set `data/fixtures/knowledge/synthetic-structured/` (the base set is untouched because its hash is pinned by every PDF test), and corrections to finding 6 plus findings 10 to 12 in the plan document. No migration.

- Guard-removal controls: 15 rules were disabled one at a time and each turned a suite red; the first run left one survivor (a call-kind check masked by the copy-number clause), the checks were split and it went red. Drifting the copied gene map also fails its test.
- Backend tiers 1, 2 and 3: 3403, 4053 and 4150 tests passed (748, 99 and 2 skipped). Each tier also reported 37 failures, all in the three recovery suites (`application-recovery`, `independent-recovery`, `recovery-cli`); they start their own PostgreSQL servers, which could not start because all 32 SysV shared-memory IDs on the machine were taken (28 with no process attached). After those 28 unattached segments were removed, the three suites passed 37 of 37, run alone outside the sandbox.
- `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm build`, `check:chunks`, `knowledge:verify --production`, `check:workflows`: passed. `test:infra` 300, `test:ci-config` 221, root `pnpm test` 47 and `test:demo-seed` 8: passed. gitleaks found nothing in the changed files.

Not run: the published FHIR IG validation (needs Java 21 and network), the browser and image tiers, hosted CI, and any HTTP read of an assessment (no route exists).

Known gap, to close before any route calls this: the review snapshot is read before the insert and is not re-checked inside the storing transaction (the patient link and disputes are). The stored binding names the exact reviews relied on, so the record is truthful, but a review changed moments earlier is not caught.
