# Durable synthetic business workflow — P2 local slice

Status: **in progress, inactive, local-only**. This branch is based on the unmerged P1 PR #169 head. Nothing here authorizes a deployment, queue registration, model call, Harness² execution, hosted CI, paid execution, or merge. The root P1 entry remains the only exported package entry until the real PostgreSQL acceptance suite is complete.

The topology is fixed: retrieve the immutable source snapshot, draft, mechanically check every candidate claim against byte spans, ask a scripted director, optionally permit one repaired draft only after a persisted valid first-director `repair` verdict, then commit a simulated outcome. At most four actor slots are reserved. There is no recursive graph scheduler or model adapter in this slice.

The durable store receives an existing tenant transaction capability and worker query capability. It owns no pool, credential, HTTP route, startup hook, or schedule. Its SQL calls are positional parameters. The existing `jobs` queue remains the only queue. A synthetic claim must be stamped inside the claim transaction with a claim UUID and increasing run fence; each business mutation must recheck the exact job, tenant, requester, lease, fence, current membership/grant/source, state and sequence. Unknown actor usage retains the full reservation. A terminal simulated outcome is unique and immutable; queue acknowledgement happens later and cannot authorize a second outcome or actor replay.

The migration creates no fixture grant, source, capacity row, schedule, or job. Test-only owners seed exact synthetic rows in a disposable PostgreSQL 16 cluster. The current local migration defines ten private tables, forced RLS on eight tenant tables, immutable source/invocation/outcome/audit guards, a down migration that refuses any nonempty synthetic table, and a restricted-app admission function. Admission serializes capacity, checks current fixture authority and exact source bytes, reserves full simulated units, then enqueues the existing ID-only job atomically. A narrow definer helper locks the active tenant because the existing jobs role has SELECT but not the UPDATE privilege that `FOR SHARE` needs; this does not grant broader table access. Claim, transition, readback, cancellation and settlement functions are still missing, so the durable path cannot run yet. In particular, do not expose a claim that can leave a live reservation without a verified terminal path.

## Trust boundary decision

P2 remains an **inactive trusted in-process fixture**. The existing backend app login can set its custom `app.current_tenant_id` and `app.current_actor` GUCs. An owned PostgreSQL test confirmed that the login can set the tenant GUC and make `membership_assert_current` return true for a synthetic membership. The P2 adapter's `withTenant` and fixture caller are trusted application inputs, not an unforgeable database identity. Tests must check that the adapter binds the supplied caller consistently and that restricted app/worker roles lack direct synthetic table rights; they must not claim resistance to a holder of the app SQL credential who can issue arbitrary SQL. A separate, reviewed session-authority design is required **before activation**. This decision does not weaken current production authorization claims outside this inactive fixture.

The original 38 acceptance families remain the delivery gate. P2-30's GUC spoof case records this explicit limitation for the inactive fixture; a later activation gate must replace it with an unforgeable session binding and hostile-login proof. No PR, CI, deployment or paid run follows from passing the present local schema smoke.
