# Synthetic assessment from stored structured revisions (032 S3)

Date: 2026-11-03
Status: Proposed plan, documentation only. Authorized by the founder's "Build spec 032 S3" and "Approved, start" (2026-11-03) for this plan PR. Nothing in this document is built, and the open decisions below are not settled by it.

## Why now

The MVP is scoped to task T-A: a staff member uploads a synthetic report, a second person reviews it, and the stored evaluation is shown (outcome, reason code, citation). The stored-result view already exists on the patient page (`PatientClinicalSections` > `ResultsList` > `StoredResult`). Nothing on staging can create an evaluation for it to show, because the lab-report pipeline and queued evaluation are refused under `NODE_ENV=production` (`docs/ops/environments.md`). Spec 032 slice S3 is the planned replacement: a contextual synthetic assessment generated from the stored structured revisions that S2 already persists.

## Findings that shape the slice (read on `origin/main` fa3d04cf, 2026-11-03)

1. **The existing evaluation path is PDF-shaped.** `EvaluationsService.store` needs an accepted capture, the report reader and `report.type === 'lab-pdf'`. The `evaluations` table has `capture_id uuid NOT NULL` and a `binding` built from text hashes and a poppler version. A structured revision has none of these.
2. **Only one caller may create evaluations.** `lab-reports/evaluation-gate.spec.ts` fails if any file other than `evaluations.service.ts` calls `insertEvaluation`. A second writer needs either a deliberate change to that test, reviewed on purpose, or a separate table.
3. **S2 is owned-local only today.** `StructuredPreviewService.assertEnabled` calls `assertLocalStorage`, which refuses `NODE_ENV=production`, requires `LOCAL_STORAGE_RUN_ID`, a loopback disposable database and a local S3 bucket. Patient-link review, the findings view and revision save are therefore not reachable on staging. S3 on staging needs an explicit decision to expose them there.
4. **Migrations 0068 and 0069 are not on staging.** `structured_report_revisions` (0068) and `structured_finding_reviews` (0069, S2c, PR #271) are marked `compat: breaking` (ledger writer and verifier rollout). `docs/ops/environments.md` records staging migrated through 0065 on 2026-10-31. The fence-close checker defect that blocked release 39713db5 is fixed on main (PR #269); whether a release has since gone out is unverified. S3's input is the reviewed findings from S2c, so the S3 migration is numbered after 0069 (0070 at `origin/main` fa3d04cf, re-checked at push time).
5. **Spec 024 D3 forbids interpretation on staging** ("there is no interpretation outside the local preview"). S3 needs that decision amended, by the founder.
6. **Content exists, but not in a form the structured path can use (corrected building 2b).** `data/fixtures/knowledge/synthetic/` holds five phenotype files and six guideline files, and the engine (`evaluate`) already answers joint tables, missing genes, unverified and disputed cells, and explicit no-recommendation cells. Three things stop the existing set serving a stored structured revision: its only combined table reads GENEA and GENEE, and the structured contract carries GENEA to GENED only; the knowledge loader refuses synthetic content in production mode, which is how staging runs; and changing the set would change the content hash that every PDF evaluation test pins. 2b therefore adds a second self-contained synthetic set, `data/fixtures/knowledge/synthetic-structured/`, and leaves the first untouched. `knowledge/cpic` stays empty; no real guideline content is used.
7. **Decisions and follow-ups are bound to `evaluations` by foreign key.** `clinician_result_decisions` (migration 0055) references `evaluation_results (id, evaluation_id, tenant_id)` and `evaluations (id, tenant_id, patient_id)`; follow-ups link to those decisions (0067). A separate assessment table therefore cannot be decided on or followed up without a migration that makes the decision target polymorphic. The `evaluation_results` outcome and reason-code vocabulary (`shown`, `held`, `abstained`, `no-published-recommendation`, `no-guideline`) already fits what a synthetic assessment produces. Widening `evaluations` touches `capture_id NOT NULL` and its foreign key, the `evaluations_check` trigger, the `evaluations_hold_consistent` check, and the capture references in migrations 0050, 0051, 0062, 0063 and 0066.

8. **The evaluation read and decision routes need the report-reader pipeline.** `GET /evaluations`, `GET /evaluations/:id` and the clinician-decision routes carry `@RequiresPipeline()`, so on staging they answer 503 `PIPELINE_DISABLED` and the patient page shows "Stored results are unavailable while report processing is disabled." A stored structured evaluation is therefore unreadable on staging until PR 3 gives those routes an enablement that does not depend on the pipeline flag (for example, the synthetic-staging profile of D3), without enabling the reader or the PDF routes.
9. **Provenance reaches the same tables (found building 2a).** An evaluation's `data_provenance` row names a parent asset, and `data_provenance_parent_kind` and `data_provenance_check()` knew only captures and acceptances. 2a widens both for a structured revision. The ledger projection of an evaluation adds the source fields for structured rows only, so no existing PDF evaluation hash changes.
10. **Naming the data origin needs the pipeline switched on (found building 2b, settled in 3a).** Every evaluation names its data origin (spec 020 E1a), and `currentDataOrigin` returns `synthetic` only when `NODE_ENV` is not production and `LAB_REPORT_PIPELINE=enabled`. Staging runs in production mode, so a structured assessment was refused there with a `DataOriginError`. 3a adds the one switch D3 asked for, `SYNTHETIC_ASSESSMENT` (below), and `structuredAssessmentOrigin`, which names `synthetic` under it and otherwise behaves exactly as `currentDataOrigin`. "Only synthetic data is held" is a declaration made by that environment's infrastructure; nothing in the application can prove it, which is why 3c must make a Terraform guard fail if any production definition sets the switch. `BUILD_VERSION` is also required by the evaluation record; the switch requires it.
11. **The S1 demonstration packages do not map to the knowledge set (found building 2b, settled in 3a).** The contract's finding values are free labels: the packages in `data/fixtures/pgx-contracts/` report `*A/*A` and a laboratory phenotype "Synthetic category A", while the knowledge maps know `*1`, `*2`, `*3` and `Synthetic Normal`. An assessment reads the diplotype and never the laboratory's phenotype, so those packages hold at the engine with `allele-not-in-definitions` (tested). Their files are pinned by hash, so 3a leaves them alone and adds `data/fixtures/pgx-structured-demo/package.json`, a separate package whose alleles the knowledge defines and which is assessed end to end over HTTP in a test.
12. **A held structured evaluation had no wording (found building 2b).** The evaluation DTO's `hold` text came only from the PDF report-hold table, so the codes migration 0070 added would have shown a held evaluation with no explanation. 2b gives the four codes it raises fixed wording in `structured-hold-codes.ts` and leaves the frozen PDF list alone.

## Decisions for the founder

| # | Decision | Recommendation |
| --- | --- | --- |
| D1 | Where S3 stores an assessment: (a) widen `evaluations` (nullable `capture_id`, a source kind, a structured binding), or (b) new append-only, ledger-covered assessment tables whose read model matches the summary shape the UI and clinician decisions already use. | (b), provided PR 2's first spike shows clinician decisions and follow-ups can bind to an assessment result without changing their rules. If they cannot, stop and re-plan. (a) edits a ledger table that every existing evaluation depends on. |
| D2 | Amend spec 024 D3 so staging may show synthetic-labelled interpretation. | Yes, scoped: every displayed assessment carries `synthetic-test-only`, `clinicalUse: not-approved`, and no recommendation wording that reads as a prescribing instruction. |
| D3 | Lift the owned-local-only gate on structured intake, findings view and patient-link review for the staging profile only. | Yes, behind a new explicit synthetic-staging profile flag that production refuses. Not by loosening `assertLocalStorage`. |
| D4 | Release order: ship the S2 migrations (0068, 0069) to staging before the S3 migration. | Yes. The S3 migration is additive and numbered after the current head at push time. |

**Status 2026-11-03.** The founder accepted the recommendations for D1 to D4. D2, D3 and D4 stand. D1 is **re-opened by finding 7**: its recommendation was conditional on decisions and follow-ups binding to a new assessment table without changing their rules, and they cannot. The two honest options are now (a) widen `evaluations` and `evaluation_results` additively (nullable `capture_id`, a source kind, a reference to the structured revision, relaxed trigger and checks by kind, and a reviewed change to `evaluation-gate.spec.ts`), which keeps decisions, follow-ups, disputes and the patient-page view unchanged; or (b) new assessment tables plus a migration making the decision and follow-up targets polymorphic, which changes two ledger-covered tables and their DTOs. Option (a) has the smaller blast radius for readers; option (b) leaves the PDF evaluation table untouched. **D1 decided (a), founder, 2026-11-03: widen `evaluations` and `evaluation_results`.** What the widening has to cover, read from the repository and not yet run on a database: `capture_id` nullable and its foreign key; a source kind and a reference to the structured revision with a check that ties them together; `evaluations_check` and `evaluations_hold_consistent`, which both assume a capture and an acceptance; a hold-code vocabulary for structured sources, since `evaluations_hold_code` lists only PDF codes; the `captureId` field in `EvaluationDto` and its mapper and ledger projections, which must accept null; `insertEvaluationProvenance`, which takes a capture id; and the ledger verifier's view of an evaluation without a capture. 2a keeps the single `insertEvaluation` method and gives its input an optional structured source, so `evaluation-gate.spec.ts` (which matches `.insertEvaluation(` and the one allowed caller) needs no edit in 2a; a service entry for a structured source arrives in 2b and is the point at which that guard is reviewed again.

## Boundaries

No clinical release is implied. A14 (equivalent PDF, FHIR and chat renderings) is out of scope for the MVP and stays a later slice.
