# Agentic session capability (option B): spec, plan and tasks

**Status: proposed, not approved.** Written 2026-10-19 from `main` `8316121`. The founder decided the same day: *"Accept option A for synthetic-only staging (I accept the stated risk), and plan option B before any real data."* This document is that plan. Scope is **P2 first**. The clinical-writes extension is a separate, later section and is not part of this plan's slices.

References to P2 cite the local, unmerged branch `feat/durable-synthetic-local` at `0530f36`; line numbers there can move before P2 merges. Everything else cites `main` `8316121`.

## 1. Problem

The P2 app entry points take the tenant and requester from the session settings `app.current_tenant_id` and `app.current_actor` (P2 `0028_agentic_synthetic.up.sql:247-248`, `:1345-1346`, `:1376-1377`). The backend sets them in `withTenant` after verifying a Cognito token (`apps/backend/src/db/database.ts:81-82`). The database cannot tell those values from forged ones: anyone holding the app's database login can set them and act as any person in any tenant. The P2 suite proves this in its GUC spoof case (P2-30), and it was accepted only for synthetic-only staging.

Things that do **not** close the gap:

- **Reusing `browser_sessions`.** The app login can INSERT and SELECT that table (`apps/backend/migrations/0026_browser_sessions.up.sql:68-69`), so it can mint a session for anyone.
- **More checks in P2's SQL.** They would read only data the app login can write or set.
- **Verifying the Cognito JWT in PostgreSQL.** That needs RS256 verification, which `pgcrypto` does not provide and RDS would need an unsupported extension for.

**Rule:** the proof of identity must be created by a principal the app login cannot imitate.

## 2. Specification

### Goals

- G1. With **only** the app database login, no one can admit, read or cancel a P2 run for any person.
- G2. A compromised backend *process* can act only for users whose live Cognito access tokens it actually holds, one request at a time, each recorded.
- G3. No new key custody: the trust anchor is a separate database login plus Cognito's own signature, not a new signing key.
- G4. P2's existing guarantees are unchanged: exact membership, grant and source revalidation, fencing, budgets, and the P2-37 guard proofs.

### Non-goals

- Clinical reads and writes. See section 6.
- Row-level security reads, which stay GUC-based for now.
- Browser cookie sessions (M5.1b/c remain separate).
- Any AWS apply or deployment.

### Actors and credentials

| Principal | Holds | Can | Cannot |
|---|---|---|---|
| Backend (`telesphoros_api`) | the app login and user requests | call P2 `admit/read/cancel` *with* a capability | insert, read or issue capabilities |
| Session issuer (**new** login `telesphoros_session_issuer`, member of NOLOGIN `telesphoros_issuer`) | its own secret, readable only by its own task role | verify a Cognito access token; call `agentic_capability_issue` | call any P2 entry point; read any table |
| Worker (`telesphoros_job_worker`) | unchanged | unchanged | issue or consume capabilities |

The login list lives in `apps/backend/src/db/provision-logins.ts:38` (four logins today). The worker login added in M2.3c is the precedent for a fifth.

### Capability

A capability is 32 random bytes, generated by the issuer and returned to the backend as base64url. The database stores only `sha256(token)`, in a new table `agentic_capabilities`. No app, worker, verifier, operator or auditor login holds any grant on it. Each row records:

- `tenant_id`, `sub` and the exact `membership_version` read under lock at issue time;
- a fixed `purpose`: `admit`, `read` or `cancel`;
- a binding: `request_digest`, recomputed in SQL from the admission input, for `admit`; or `run_id` for `read` and `cancel`;
- database-stamped `issued_at`; `expires_at` = `issued_at` + 60 s; and `consumed_at`.

`agentic_capability_issue(tenant, sub, membership_version, purpose, binding, token_hash)` is SECURITY DEFINER, granted only to `telesphoros_issuer`. It runs `membership_assert_current` under its tenant (the same helper P2 uses, `0017_membership.up.sql:73`), refuses an inactive tenant, stamps the time with `clock_timestamp()` and inserts the row.

### Consumption (P2 changes)

`admit`, `read` and `cancel` gain a `p_capability text` argument. Inside each function's own transaction:

1. Hash the token and lock the row `FOR UPDATE`.
2. Check `expires_at > clock_timestamp()` **after** the lock (the same rule as `agentic_synthetic_fresh`).
3. Check that the row is unconsumed, the purpose matches, the binding matches, and the tenant, sub and membership version equal the caller's.
4. Set `consumed_at`, then proceed with today's checks.

Rollback restores the capability, so consumption is atomic with the decision. The tenant and requester come **from the capability row**, never from the GUCs. The GUCs are still set for RLS on other tables, but P2 stops reading them for identity.

### Issuer flow

The browser sends its request to the backend, which verifies it as today. The backend then calls the issuer over the internal network with the user's access token, the purpose and the binding. The issuer:

- verifies the token itself, with the same checks as `CognitoTokenVerifier` (`apps/backend/src/auth/cognito-token-verifier.ts:45-54`: signature against the JWKS, issuer, `token_use=access`, `client_id`, expiry, issued-at age);
- resolves the membership;
- issues the capability, writes a security event (who, purpose, binding digest; never the token) and returns the raw token once.

The backend passes it straight to the P2 call.

### Residual risk (stated, not solved)

A compromised backend process can relay real users' in-flight tokens to the issuer during their token lifetime (at most 1 h). Mitigations are a per-subject issue rate limit, purpose and binding pinning, and an audit trail per issuance. A stolen **issuer** login can forge capabilities; that credential is single-purpose, held by a separate task role, and never used by humans.

## 3a. Evidence for the decisions (researched 2026-10-19)

The founder asked for evidence before following any recommendation. Every source below was opened, and each quote was checked against the page text: by grep on raw text for the RFCs, ASVS, NIST 63C and the OWASP cheat sheet, and by reading the fetched page for the AWS documentation. Anything without a source is labelled **judgment**. Section 3 is left as written; where the evidence changes a recommendation, the change is stated here and waits for the founder.

**A correction to section 2.** The residual risk says relayed tokens live "at most 1 h". In this repo, access tokens live **15 minutes** and revocation is on (`infrastructure/terraform/cognito.tf:103-112`, pinned by `guard.test.mjs:48-50`). The relay window is therefore 15 minutes. Cognito notes that revoked tokens *"will still be valid if they are verified using any JWT library"* ([token revocation](https://docs.aws.amazon.com/cognito/latest/developerguide/token-revocation.html)). The issuer's own `membership_assert_current` check is what stops a removed person, not Cognito revocation.

### D1. Issuer runtime: evidence modestly favours ECS, with two conditions (confidence: medium)

| Evidence | Source | Direction |
|---|---|---|
| "proxies are recommended for production" for Lambda with RDS, and the proxy is billed hourly | [Lambda with RDS](https://docs.aws.amazon.com/lambda/latest/dg/configuration-database.html) | ECS: Lambda adds RDS Proxy, which itself reads the login's secret |
| A Fargate task "is always ready to handle requests"; cold starts "can impact performance of applications that require low-latency responses" | [Fargate or Lambda guide](https://docs.aws.amazon.com/decision-guides/latest/decision-guides/fargate-or-lambda.html) | ECS: the issuer sits on the synchronous request path |
| Cold starts are more common for rarely called functions; environments are recycled "every few hours" | [Lambda execution environment](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html) | ECS: pilot volume is low |
| "you typically pay less with Lambda at lower traffic volumes" | Fargate or Lambda guide | **Lambda** |
| Lambda invocation is authenticated by IAM (a resource policy names the caller), with no network listener | [Lambda resource policies](https://docs.aws.amazon.com/lambda/latest/dg/access-control-resource-based.html) | **Lambda** |
| The repo has **no** internal service-to-service networking (no Service Connect, Cloud Map or internal load balancer); the worker accepts no inbound traffic (`worker.tf:111`) | repo, `main` `8316121` | **Lambda**: an ECS issuer needs new ingress *and* an application-level check of its caller |
| The only Lambda in the repo has no VPC and no database (`lambda.tf`) | repo | neutral: it is no precedent for a database-connected Lambda |
| The worker already has a dedicated execution role that reads only its own secret (`worker.tf:183-187`, `200-211`) | repo | ECS: the isolation pattern exists and is tested |
| A secret injected through `secrets` is not refreshed after rotation; it needs a new task or a forced deployment | [ECS secrets as environment variables](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html) | condition for ECS |

**Revised recommendation:** keep **ECS, same image**, on two written conditions. First, the issuer gets its own execution role and task role, as the worker does, because a shared execution role would let the API read the issuer's secret. Second, slice 2 must design and price two things it was silent about: the internal ingress path and authentication of the caller. The choice between those costs and Lambda's (RDS Proxy, a VPC attachment, cold starts) is a **judgment**. No AWS document gives a verdict for this case.

### D2. Capability lifetime 60 s: supported as a ceiling (confidence: high for the ceiling; the exact value is judgment)

| Evidence | Source |
|---|---|
| Authorization code lifetime "up to 1 minute for L3 applications" (L1/L2: 10 minutes) | OWASP ASVS 5.0.0, requirement 10.4.3 |
| "A maximum authorization code lifetime of 10 minutes is RECOMMENDED" | RFC 6749 §4.1.2 |
| A single-use back-channel assertion reference "SHOULD have a validity time window of no more than five minutes" | NIST SP 800-63C-4, back-channel presentation |
| Proof acceptance "on the order of seconds or minutes" (no number) | RFC 9449 (DPoP) §11.1 |
| Against: a 30 s TOTP lifetime | ASVS 5.0 6.5.5. This is a weak analogy: a human-typed six-digit code is guessable, and a 256-bit capability is not |

**Revised recommendation:** keep **60 s, single use**, as the ceiling ASVS L3 sets. The database must stamp both `issued_at` and `expires_at` (already in section 2), so clock skew between servers cannot widen the window. RFC 7519 allows "a few minutes" of leeway when two clocks are involved. Shortening below 60 s does little: the relay risk is bounded by the 15-minute access token, not by this number.

### D3. Rate limit 30 per person per minute: no source gives a number (confidence: the number is **judgment**)

| Evidence | Source |
|---|---|
| Limits must be "documented, including both per-user and globally" | ASVS 5.0.0, requirement 2.1.3 (L2) |
| Anti-automation controls must exist against "excessive calls to application functions" (no number) | ASVS 5.0.0, requirement 2.4.1 |
| "not rely on a single predictable volume limit"; consider short (burst) and long windows | OWASP Credential Stuffing Prevention Cheat Sheet |
| Rate limiting should be "fine tuned based on the business needs", per user and per operation | OWASP API Security Top 10 2023, API4 |
| AWS WAF rate rules are "not intended for precise request-rate limiting", and key only on raw header values | [WAF rate-based caveats](https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-type-rate-based-caveats.html) |
| NIST's 100 and ASVS 4.0.3's 100 per hour count **failed** authentications, not successful issues | NIST SP 800-63B-4 §3.2.2; ASVS 4.0.3 2.2.1. Not applicable |

**Revised recommendation:** replace the single fixed 30/min with **separate limits per purpose** (admit, read, cancel), each with a burst tier and a sustained tier, plus a global limit. Enforce them atomically in PostgreSQL next to the capability insert, and keep WAF as an outer per-IP layer only. Choose the values by counting issues per person, per purpose, per minute in count-only mode on synthetic staging, then set each limit at a stated multiple of the observed maximum, reported with its sample size and window. Until that measurement exists, any number is a provisional **judgment**, and the document will say so. Not measured: whether one page fires several `read` issues at once.

### D4. Shared verifier package: evidence says it is not needed (confidence: medium)

| Evidence | Source |
|---|---|
| The worker ships as *"one self-contained bundle (its workspace packages are compiled in)"* inside the API image | `infrastructure/docker/api.Dockerfile:12-14`, `:19` |
| `CognitoTokenVerifier` depends only on `jose`, `zod`, `@telesphoros/shared-types` and Nest's `Logger`, all of which already ship in the image | `apps/backend/src/auth/cognito-token-verifier.ts:1-5` |
| AWS recommends caching keys by `kid`; the verifier already does (10-minute cache, cooldown on an unknown `kid`) | [Cognito JWT verification](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html); `cognito-token-verifier.ts:38-42` |

**Revised recommendation:** do not move the verifier. Build the issuer as a **second bundled entry point** that imports the existing `CognitoTokenVerifier` and its 18 tests unchanged, as the worker does. That removes a refactor from slice 2. A shared package becomes worth having only if a third process needs the verifier (**judgment**).

## 5. Tasks and verification

Each slice follows the Working agreements in `docs/STATUS.md`: plan approval, three test tiers, defect injection, hand-written oracles and faithful reporting.

1. **Slice 1:**
   - Positive control: an issue followed by a direct consume succeeds.
   - Every login except the issuer gets `42501` on the table and the issue function.
   - Issuing for a removed or bumped membership, or an inactive tenant, is refused.
   - `expires_at` is set from the database clock.
   - Down/up passes the catalog-snapshot test, P2-32 style.
2. **Slice 2:**
   - The verifier rejects every case the backend's verifier rejects, using the same fixtures.
   - The rate limit refuses the request after the limit.
   - The security event never contains the token.
   - The Terraform guard pins the task role and the separate secret, with weakened-copy controls.
3. **Slice 3 (the acceptance proof):**
   - **Hostile login:** with only the app login and any GUC values, admit, read and cancel for another person are refused. Positive control: the same calls succeed with an issued capability.
   - **Single use:** a replayed capability is refused, and two parallel uses yield exactly one success.
   - **Expiry:** a capability presented after 60 s is refused, including when it arrives after a lock wait.
   - **Binding:** a different tenant, sub, membership version, request digest, run or purpose is refused.
   - **Rollback:** a failed admission leaves the capability unconsumed.
   - **Mutants, each shown red:** the consume lock, the after-lock expiry check, single use, each binding field, and GUC identity left in place.
   - The full P2 suite and the P2-38 gate re-run on the slice's candidate.

## 6. Later: clinical-writes extension (not part of this plan)

Once slice 3 holds, the same capability could protect clinical **writes**. It is out of scope here because:

- **Latency and availability.** Every write gains an issuer round trip, and an issuer outage blocks writes. That needs its own SLO and failure-mode decision.
- **Purpose catalogue.** Each write needs a fixed purpose and binding (report correction, membership change, upload commit, and so on). That's a design pass over every write path.
- **Cookie sessions.** Moving `browser_sessions` INSERT from the app login to the issuer would make cookie sessions unforgeable too. That interacts with the open M5.1b/c work and must be planned there.
- **Reads.** RLS policies read the tenant GUC per row, so capabilities don't fit reads directly. An unforgeable read path is a separate design (for example, definer read functions keyed by a capability).

A separate security review of today's GUC-based RLS is recommended either way. It has the same forgeability property as P2 under option A.
