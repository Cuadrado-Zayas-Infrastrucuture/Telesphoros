# Synthetic patient setup and upload handoff

A **clinician** adds a synthetic patient from the upload page: when the roster is empty the **Add a synthetic patient** form opens by itself, and otherwise the same form is one click away. It takes a synthetic label (letters, numbers and hyphens, up to 40 characters, for example `SYN-0002`; never a name or a real identifier), creates the patient, and selects it. Nothing is created until the clinician presses **Add patient** (or Enter in the label field). Do not resolve an empty roster by assigning clinical permissions to an administrator.

The form calls the authenticated `POST /api/v1/patients` API with the strict input `{ "label": "SYN-0001", "requestId": "<uuid>" }`. The caller must hold the clinician role in the target organization; the server takes organization and identity from the verified caller, not from the request body. The page keeps one request id per label it is trying, so a retry after a lost answer replays the patient the first request created instead of making a second. A label that is already taken is refused (409) with a plain message and nothing is selected. The same request remains available to an API/setup operator who assists a clinician, without database-owner inserts or privileged credentials replacing authorization.

An `admin` alone manages membership and invitations, but cannot create or read clinical patients. A person who needs clinical work holds the separately assigned clinician role. Reader/reviewer status does not grant patient creation. See [roles and membership](../auth.md).

Patient search screens and a full onboarding workflow remain separate product work. Before 2026-10-25 the upload page only selected an existing patient and told the user to ask a clinician; the 2026-10-14 verification note records that earlier behaviour. The add-patient form changes no API, role, tenant boundary, upload behaviour or synthetic-only requirement.
