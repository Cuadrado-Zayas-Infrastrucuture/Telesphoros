# Database and storage

PostgreSQL 16 holds metadata; object storage (S3) holds report files. **Synthetic data only** until the
AWS BAA is executed and the compliance prerequisites are complete.

Rules enforced **by the database itself** (each is asserted by a test that tries to break it):

- **UUID primary keys** on clinical API records, matching their public ids. Ledger heads and migration history instead use tenant/version keys.
- **Tenant records have `tenant_id` (the organization that may see the row) and `created_by` (the individual who made it).**
  Clinical parent foreign keys are **composite** (`id, tenant_id`), so a child row cannot point at another tenant's parent even if
  application code were wrong. Neither column can change after insert (a trigger refuses it, even for the table owner).
  (Migration 0003 renamed `owner_id` to `tenant_id`; each former owner became a tenant of one.)
- Global containment/clearance and system tables deliberately have different fields and relationship rules; see the [complete table-class acceptance matrix](verification/phase3a-data-integrity.md). Evaluations reference `reports(id, patient_id, tenant_id)`, so two different patients in one tenant cannot be joined by independent FKs.
- **Every foreign key states `ON DELETE RESTRICT`.** Clinical history is never silently cascaded away.
- **Actors (0023).** `system:<job type>` is the name a background job acts under and is **never a person**: a CHECK on every table that records a human decision or assertion (`<table>_created_by_human`; on `patient_identifiers` also `withdrawn_by`) and on `tenant_memberships.sub` refuses it, so no independence rule can be met by a job.
- **Soft delete** (`deleted_at`). The application role has no `DELETE` privilege at all. Soft-deleting a patient
  that still has live reports (or a report with live evaluations) is refused by a trigger, mirroring `RESTRICT`.
- **Unique:** one live label per tenant (case-insensitive; a soft-deleted row frees its label); one report per
  storage key (the same file cannot be registered twice).
- **Report registration retries (0014):** an optional UUID `requestId` on `POST /api/v1/reports` reserves `(tenant_id, created_by, creation_request_id)` atomically. The immutable fingerprint covers the original patient ID, type, filename and byte size. Same key/input returns the current report with its original ID (201); changed input or a soft-deleted report returns 409. Other creators/tenants have separate key namespaces; omitted keys retain ordinary creation. Keys and fingerprints are internal, never report DTO fields. Metadata corrections do not overwrite the original fingerprint, and a trigger forbids rekeying or changing it. This does not deduplicate file contents or retain client retry state across browser restarts.
- **Patient creation retries (0039):** the same pattern on `POST /api/v1/patients` (audit item 25). An optional UUID `requestId` reserves `(tenant_id, created_by, creation_request_id)`; the immutable fingerprint is of the original label. The same id and label returns the patient with its original ID (201) even after its label was edited, and where a repeat without an id answers 409 because the label exists; the same id with another label, or after the patient was deleted, returns 409 (`request-id-reused`). Other people and organizations have separate id spaces. The id and fingerprint are never in the DTO, a trigger forbids changing them, and `PUT` takes no id. Invitations and identifier registration follow in their own changes.
- **Identifier registration retries (0040):** the same pattern on `POST /api/v1/patients/:id/identifiers` (audit item 25). An optional UUID `requestId` reserves `(tenant_id, created_by, creation_request_id)`; the immutable fingerprint is of the patient, the assigning system and the keyed digest (never the value). The same id and body returns the identifier with its original ID (201), also after it was withdrawn (its status says so), where a repeat without an id answers 409 `identifier-in-use`. The same id with another number or patient returns 409 `request-id-reused`. A number another patient holds is still refused and still records the possible duplicate. Neither the id nor the fingerprint is ever in the DTO, and a trigger forbids changing them.
- **Invitation retries (0041):** the same pattern on `POST /api/v1/members/invitations` (audit item 25), through a new SECURITY DEFINER function `invitation_create_keyed` beside `invitation_create` (the application role cannot write the table). An optional UUID `requestId` reserves `(tenant_id, created_by, creation_request_id)`; the immutable fingerprint is of the address's keyed digest and the roles as a set (never the address). The same id and body returns the invitation with its original ID (201) whatever its status is now (cancelled, expired or fulfilled show as such); a repeat without an id answers 409 `invitation-pending`; the same id with another address or roles answers 409 `request-id-reused`. The id and fingerprint are never in the DTO, and a trigger forbids changing them.
- **Capture decision retries (0044):** the same pattern on `POST /api/v1/captures/:id/decision` (inherited audit item 1). A retried decision used to make a second acceptance row, and an evaluation made from the first was then no longer built on the newest decision. An optional UUID `requestId` reserves `(tenant_id, created_by, creation_request_id)` on `capture_acceptances`; the immutable fingerprint is of the capture, the decision and the note. The same id and body returns the decision with its original ID (201) and writes nothing, so an evaluation made from it stays current; the same id with another decision, note or capture answers 409 `request-id-reused`; a repeat without an id is a new decision, as before. The table is append-only already, so no guard trigger is needed; the ledger's projection names its columns, so neither new column reaches an event hash. Repeats of one id queue on an advisory lock, so two at once leave one decision and one note. The id and fingerprint are never in the DTO. Rollback refuses while any is set unless the operator sets `telesphoros.allow_capture_decision_retry_drop=yes`.
- **Dispute raise retries (0045):** the same pattern on `POST /api/v1/cell-disputes`. A retried raise used to make a second dispute for the same cell, and a dispute in force holds the evaluations that rely on its cell, so after the first was dismissed the duplicate kept the cell disputed until someone also decided it. An optional UUID `requestId` reserves `(tenant_id, created_by, creation_request_id)` on `cell_disputes`; the immutable fingerprint is of the guideline, the cell and the note (not the version or the file hash, so a repeat after the knowledge was re-signed still finds its dispute). The same id and body returns the dispute with its original ID (201) and its status now, and writes nothing; the same id with another cell or note answers 409 `request-id-reused`; a repeat without an id is a new dispute, as before. The table is append-only already, so no guard trigger; the ledger's projection names its columns, so neither new column reaches an event hash. Repeats of one id queue on an advisory lock. The id and fingerprint are never in the DTO. Rollback refuses while any is set unless the operator sets `telesphoros.allow_dispute_retry_drop=yes`.
- **Hardening 1 (0046):** the evaluation JSON columns carry size caps (`evaluations.occurrences` 1 MiB, `gene_inputs` 256 KiB, `binding` 16 KiB; `evaluation_results.gene_evidence` 256 KiB, `citation` 16 KiB, measured on the JSON text), because the tables are immutable and an oversized row could never be corrected. The caps are judgements set far above anything the 200-gene input limit produces; raise one in a new migration if a real payload nears it. The two upload policies name `telesphoros_app` and `telesphoros_jobs` instead of `PUBLIC`. `security_events` has row-level security on (not forced) with one policy for the auditor.
- **Suspended organizations (0047):** `app_tenant()` answers NULL for a registered organization whose status is not `active`, so every policy and definer function that binds through it (47 policies, the ledger, queue and outbox writers) reads and writes nothing for a suspended organization, at once, including with a capability minted before the suspension. `app_tenant_bound()` is the unchanged binding; the policies of `tenants`, `tenant_memberships`, `invitations` and `browser_sessions`, and the functions `security_event_append`, `membership_assert_current`, `member_sign_out` and `member_admin_context`, read it, so admission can still see the organization, record the refusal and sign the person out. **Not covered:** an organization that was never registered can still be named through the setting in `guc`/`dual` mode; that closes when binding becomes capability-only, because the issuer mints only for a registered, active organization. Costs one primary-key lookup on `tenants` per statement (about 2 microseconds measured).
- **0014 rollback:** preserves report rows but removes retry identities. Populated identities refuse rollback unless the operator explicitly sets `telesphoros.allow_report_retry_drop=yes` after a blast-radius review/export/recovery plan; reapplying 0014 alone cannot recover removed identities. The setting does not grant DDL privileges. Lock waits are bounded at two seconds; migration execution at thirty seconds. No operational rollback or shared-data change is authorized by the synthetic tests.
- **Checks:** label and filename formats, size 1 byte to 10 MB, valid status/type/strength, lowercase hex SHA-256,
  and "uploaded implies key + checksum + content type".
- **`created_at` / `updated_at`** on the legacy mutable tables; `updated_at` moves automatically unless the writer sets it. Append-only and system tables use class-specific fields.
- **`seq`** (identity) gives stable creation order for pagination, because timestamps can tie.
- **Indexes** support tenant/filter/order and parent uniqueness; exact query-facing definitions and real query plans are checked. Some append-only event FKs deliberately lack a dedicated child index; application roles cannot delete those parents.

### Recommendation relationship migration (0012/0013, historical)

0012 adds the tenant/patient/id uniqueness to reports and a `NOT VALID` FK from recommendations; it enforces new references without changing historical rows. 0013 validates in a separate transaction. Both bound lock waits to 2 seconds and statements to 30 seconds. `NOT VALID` avoids the initial historical-row scan, not all locking; referenced uniqueness still requires an index build. If legacy mismatches exist, 0013 fails and rolls back while 0012 remains committed. Pending 0013 keeps readiness at 503; the catalog acceptance gate also rejects `convalidated=false`. Stop: do not reassign patients, delete/soft-delete rows or run a quarantine script automatically. Founder approval of a specific tenant-scoped, evidence-preserving remediation script is required before any operational repair and retry. Clean synthetic databases validate automatically. Rollback of 0013 recreates the enforced unvalidated FK; rollback of 0012 removes it and the added unique constraint. Nothing here was applied to a live/shared database.

**Dropped in 0043.** The `recommendations` table is gone: nothing wrote it in production, and the route and code that read it were removed in #19 and #39. Recommendations come from `evaluations` and `evaluation_results`. The migration is labelled `breaking`, refuses to run while the table holds a row (`telesphoros.allow_recommendations_drop=yes` allows it on purpose), and replaces the report soft-delete guard so it no longer names the table. Its `down` recreates the table empty, with the policy as 0032 left it. The text above describes 0012 and 0013 as they were applied.

## Row-level security (defence in depth)

The API connects as a login role that is a member of `telesphoros_app`: **not** a superuser, **not** the table
owner, **no** `BYPASSRLS`, **no** `DELETE`/`TRUNCATE`/DDL. Each request runs in **one transaction** that first
executes `set_config('app.current_tenant_id', <tenant from the token>, true)` (transaction-local, so it cannot leak to the
next request on a pooled connection). The policies compare `tenant_id` to that setting; **if it is missing the role
sees nothing** (fail closed; code still setting the old `app.current_owner_id` therefore sees nothing either). Every query also names `tenant_id` explicitly, so two independent layers protect each
row. Tests prove each layer separately and together (`test/db/rls.pg-spec.ts`, `repositories.pg-spec.ts`).

| Role | Used by | Can |
| --- | --- | --- |
| admin (a superuser, or a role with `BYPASSRLS`) | backup, restore (`DATABASE_ADMIN_URL`) | everything; bypasses RLS (needed so a backup sees every row) |
| migrator (the table owner) | migrations, the `membership`, `tenant` and `invite` commands (`DATABASE_MIGRATOR_URL`) | DDL on what it owns; **not** a superuser and **no** `BYPASSRLS`, so on a table with `FORCE ROW LEVEL SECURITY` and policies only for other roles it sees **no rows**. A down migration that must look at the rows first (a "refuse if populated" guard) therefore either switches to the role that owns the table or lifts `FORCE` for the check inside its own transaction (`test/db/down-guards-as-migrator.pg-spec.ts` runs every such guard as this login) |
| `telesphoros_app` (group) + a login user | the API (`DATABASE_URL`) | `SELECT/INSERT/UPDATE` on `patients`, `reports`; read `schema_migrations`; **bound by RLS** |

The ledger adds four more `NOLOGIN` roles (`telesphoros_ledger`, `telesphoros_redactor`, `telesphoros_ledger_verifier`,
`telesphoros_ledger_operator`) with narrow rights; what each may do, how the migrator and the verifier and operator logins are
provisioned, and what a restore needs: [docs/ops/ledger-roles.md](ops/ledger-roles.md). Tests for them live in `apps/backend/test/db/ledger-*.pg-spec.ts`.
The stored lab PDF is pinned to an object version and protected by the database; see [docs/ops/report-evidence.md](ops/report-evidence.md).

**Server-side limits (provision-logins).** The pool sets `statement_timeout` and `idle_in_transaction_session_timeout` for the code that uses it; that does not bind a second client or a stolen login. Provisioning therefore also sets role-level defaults and a connection ceiling on every login (`LOGIN_LIMITS` in `src/db/provision-logins.ts`: API 10 s / 15 s idle / 5 s lock, 50 connections; worker 20; issuer 20; verifier 120 s, 20; migrator no statement timeout, 5) and revokes `TEMPORARY` on the database from `PUBLIC`. It repairs them on every run and reports them as checks. The numbers are judgements; the connection ceilings are **assumed** to sit under the instance's `max_connections`. Terraform checks each login's connections at the deploy peak against its ceiling, and the sum against `db_connection_budget` (`infrastructure/terraform/database-connections.tf`). `connection-limits` reads both on a live instance.

The login user and its password are provisioned **outside the repository** (locally by
`infrastructure/docker/postgres-init.sql`; in AWS by an operator step, with the password in Secrets Manager).

## Migrations

Plain numbered SQL, no ORM: `NNNN_name.up.sql` + `NNNN_name.down.sql`, applied by `src/db/migrator.ts`.

```bash
pnpm --filter @telesphoros/backend build                    # the CLI runs from dist/
export DATABASE_MIGRATOR_URL=postgres://<owner>@<host>/<db>
pnpm --filter @telesphoros/backend db:status
pnpm --filter @telesphoros/backend db:migrate               # apply pending
pnpm --filter @telesphoros/backend db:migrate:down          # revert the last one
```

- Each migration runs in **its own transaction**; a failure rolls back completely and names the migration.
- An **advisory lock** makes two simultaneous deploys safe (the second waits, then finds nothing to do).
- A **checksum** is stored; **editing an applied migration is refused**. Add a new migration instead.
- Versions must be contiguous and every migration needs a `down`.
- **Adding a migration edits no test list.** Specs that need the history (everything above migration X, how many steps to revert to X, how many were applied) ask `apps/backend/test/helpers/migration-history.ts`, which reads the directory; do not write version lists or step counts into a spec. The one place that pins history is `apps/backend/test/migration-history.spec.ts` (no database needed): it pins every migration that had shipped when the pin was written by name and checksum, so editing, removing, renaming or renumbering one fails on a fresh checkout, and it fails on a stray file the loader would skip. A new migration is checked for shape only there (contiguous, one name per number, an up and a down); the pin is extended on purpose, in a change of its own.
- `/api/v1/ready` returns **503 while migrations are pending, history disagrees with the shipped versions/checksums, the database holds newer migrations that are not all declared `expand`, or metadata cannot be read**. It reuses the migration runner's strict history validator with the existing read-only application grant; it never applies migrations or repairs history. `/api/v1/health` stays 200. Failures keep the generic readiness envelope and existing two-second deadline.
- **Compatibility labels:** an older binary accepts newer history only when it is contiguous and every newer migration was recorded as `expand` (see [Migration labels](#migration-labels)); an unlabelled or `breaking` one is refused. Checksums cover both the `up` and `down` SQL. Preserve applied files and investigate mismatches; do not normalize history to silence readiness. This does not inspect the physical schema, verify migration timestamps, or change startup/request admission. The separate compatibility contract remains open; see [T02 verification](verification/t02-readiness.md).

## Migration labels

From migration 0028 every `.up.sql` must start with a label in its leading comment block (blank lines and `--` comments before the first statement):

```
-- compat: expand
```

- **`expand`**: tasks running an older image keep working once this is applied. Additive only: new tables, new nullable columns (or `NOT NULL` with a default), new indexes, new grants.
- **`breaking`**: anything else. Use it when unsure; over-labelling only costs an outage window.
- **An `expand` migration may not contain** `DROP`, `RENAME`, `ALTER COLUMN ... TYPE`, `SET NOT NULL`, `ADD COLUMN ... NOT NULL` without a default, `REVOKE`, `TRUNCATE` or `CREATE OR REPLACE`. So redefining a function, or dropping and re-adding a constraint, is `breaking`. Data rewrites and row-level-security policy changes on existing tables are not checked automatically and can still break older code: label them `breaking`.
- **Two more rules, for a table that already existed** (one the same file does not create). An `expand` migration may not add a trigger, a `CHECK`, `FOREIGN KEY`, `UNIQUE`, `EXCLUDE` or `PRIMARY KEY` constraint, or a unique index to it: each can refuse a write older code still makes. And any migration (either label) that runs `ALTER TABLE`, `CREATE INDEX`, `CREATE`/`DROP TRIGGER` or `CREATE`/`ALTER`/`DROP POLICY` on it must first run `SET LOCAL lock_timeout = '2s';` (any non-zero value, as a statement of its own; a function's own `SET lock_timeout` clause does not count), so a lock it cannot get fails the migration instead of queueing every writer behind it. DDL run through `EXECUTE` or a `DO` block is not seen. `GRANDFATHERED` in `migration-lint.ts` excuses, by number and rule, applied migrations that predate these rules (today only 0034); the lint spec checks that every entry still needs its excuse and that the same text under another number is reported.
- The migration lint (`apps/backend/src/db/migration-lint.ts`, run by a unit spec in every test tier) enforces the above and refuses a file that ends inside a quote or comment. Migrations 0001 to 0027 predate the label, are unlabelled and count as `breaking`.
- The label is part of the file's checksum, so it cannot change after the migration is applied, and the migrator records it in `schema_migrations.compat`. Readiness reads that column for migrations it does not know. A label placed after the first statement is ignored, and the lint says so.

How this changes a release (outage window or not, rollback, and the two-release rule for destructive changes) is in [api-hosting.md](ops/api-hosting.md#releasing-after-f4-exists).

## Database TLS

One setting decides how every database connection is encrypted: `DATABASE_SSL` (`disable`, the default, for local development and tests; `require` in AWS, and production refuses anything else).

- **The connection URLs carry no TLS parameters.** Any `ssl...` or `uselibpqcompat` parameter in `DATABASE_URL`, `LEDGER_VERIFIER_DATABASE_URL`, the migrator or admin URL is refused, by name only (the message never quotes the URL). The reason: node-postgres lets URL parameters *replace* an explicit `ssl` object, so `?sslmode=disable` connected without TLS and `?sslmode=no-verify` switched verification off even when the code asked for verification. In libpq (`pg_dump`, `pg_restore`), `sslmode=require` encrypts but does not verify the certificate.
- `require` means TLS 1.2 or newer with the certificate chain and host name verified against the system authorities plus `NODE_EXTRA_CA_CERTS` (the RDS authority bundle goes there in the image).
- The command-line tools get the same guarantee through `PGSSLMODE=verify-full`, `PGSSLROOTCERT` (from `DATABASE_SSL_CA`, else `NODE_EXTRA_CA_CERTS`) and `PGSSLMINPROTOCOLVERSION=TLSv1.2`; with no authority file they refuse rather than connect unverified.
- Every `Pool` and `Client` is built from `pgClientConfig(url)` in `src/db/tls.ts`; `connection-guard.spec.ts` fails the build for any file that builds one another way.
- Proved against real TLS (`test/db/tls.pg-spec.ts`: a throwaway authority, a matching and a mismatched certificate, an untrusted authority, and URLs carrying `sslmode`), and by breaking the code in eleven ways with a green control. **Not verified:** a connection to a real RDS instance (nothing is applied in AWS).

## Report files

A report file is stored by the validated server intake (M2.2b; the earlier browser-to-bucket upload routes were removed):

1. `POST /api/v1/reports/:id/upload-attempts` declares an attempt with `{ requestId, revision, contentType, sha256 }`. The object key is generated by the
   server: `reports/<hash of tenant>/<report id>/intake/<attempt id>`.
2. `PUT /api/v1/reports/:id/upload-attempts/:attemptId/bytes` sends the raw bytes **to the API**, which checks size, content type, SHA-256 and a bounded
   structural parse before it writes anything to the bucket, pins the stored version and marks the report uploaded. It does not take the client's word for any
   of them, and a refused file never reaches the bucket.

Known gaps: a validated file that was stored but never committed stays in the bucket (the operator sweep, `uploads sweep`, only returns its quota; deleting it
is a break-glass act); there is no virus or content scan; report files are versioned but **not** replicated to a second region by the current Terraform.

## Scheduling the real-service test suites

When `TEST_DATABASE_URL` is set, the backend Jest configuration runs one suite at a time. All suites share one PostgreSQL instance; host CPU-count worker defaults can overload it with concurrent migrations, restores and checkpoints. The restore advisory lock only excludes other participating restore suites, not unrelated database suites.

This controls scheduling, not coverage: existing test deadlines and assertions remain, as do multi-session/writer concurrency tests within a suite. Unit-only runs retain Jest's worker defaults. Do not override the service-run worker count to gain speed without rerunning the resource-contention controls. See [verification](verification/restore-test-scheduling.md).

The three native `backup-restore`, `ledger-backup` and `ledger-restore-check` suites use an explicit 30-second test/hook budget for migrations, dump/restore subprocesses and forced checkpoint cleanup. The global Jest unit-test default remains unchanged. Ledger test copies are released after each test; only the ledger-backup suite's shared source and baseline backup survive until suite teardown. ## Explanation receipts (0048)

`agentic_explain_receipts` stores the receipt of an explanation run of the LLM harness (`specs/003-llm-harness`, outcome v2 in `apps/ai-service/src/outcome-v2.ts`): digests, fixed reason codes and counters, never text. Every text column is bound to a pattern or a list, so a result, a phenotype or a model word cannot be written; the evidence and output digests must be keyed (`hmac-sha256:`), so a plain SHA-256 is refused by the table as well as by the code. The table is owned by the NOLOGIN role `telesphoros_jobs` (like the synthetic agentic tables), forced row-level security, and no login holds a table privilege. Only the application login may run `agentic_explain_receipt_append` and `_read`; each takes its caller from a presented capability through the family's own `agentic_explain_identity()` (the body of `agentic_synthetic_identity()`, copied so that dropping the synthetic family later cannot break receipts), so a receipt is written or read only for the caller's own organization, and a suspended organization (0047) is refused. The worker cannot present a capability and is not granted them. `provision-logins` checks these rights and that no login touches the table.

**Retention and erasure (decided 2026-10-25).** A receipt is never updated, and a delete is refused, for every role including the owner, until the row is 2190 days (6 years) old; the two triggers are `ENABLE ALWAYS`, so `session_replication_role = replica` does not skip them. The purge, `agentic_explain_receipt_purge(tenant or NULL)`, is an operator function that no login can run: the migrator runs it through `SET ROLE telesphoros_jobs`, and it reaches suspended and offboarded organizations too. There is no row erasure on request: the receipt holds no text, and the path to make its digests unlinkable is destroying or rotating the digest key. Counsel is to confirm that before real data (R5 in `ai-safety-and-hallucination-controls.md`).

**Bounded growth.** Receipts cannot be deleted for six years, so an organization may add at most 1000 an hour (`RATE_LIMITED` beyond that; an initial value, adjustable by migration; the count is not locked, so concurrent appends can overshoot slightly).

**What no migration can close** (same class as `security_events`): the owner, reachable by the migrator through `SET ROLE`, can disable or drop the triggers, drop the table (`DROP TABLE` fires no row trigger; the down migration's `telesphoros.allow_receipts_drop` refusal is the only protection against that), or insert a back-dated row and then delete it. The table must stay unpartitioned, or an event trigger must be added, because dropping or detaching a partition does not fire the row trigger. Mitigation is database audit, not this migration. Not in this migration: the run, usage and cap tables that give the explanation run durable fencing and fleet and tenant caps (the next slice).

## Explanation runs (0049)

`agentic_explain_runs` is the durable run of an explanation (`apps/ai-service/src/explain.ts`): the idempotency key (kept as a hash), the request (kept as a **keyed** digest, `hmac-sha256:`, because the evidence is a small space), the fenced state, the sequence and the deadline. No text. Ownership and access are those of the receipts: owned by `telesphoros_jobs`, forced row-level security, no login holds a table privilege, and four capability-bound functions for the application login only (`agentic_explain_run_admit`, `_get`, `_advance`, `_cancel`) that see only the caller's own organization and requester; a suspended organization is refused.

**State machine.** The 31 legal moves are one explicit list in SQL (`agentic_explain_transition_ok`), checked against `canTransition` in `apps/ai-service/src/kernel.ts` by a test that reads the migration, and enforced again by a row trigger, so even a caller with table access cannot make an illegal move. `advance` is a compare-and-swap on state, sequence and fence under a row lock: of any number of concurrent advances from the same state exactly one wins and the rest are stale. `cancel` raises the fence, so a worker that still holds the old one is stale at its next step. A finished run is frozen; sequence rises by one; the fence rises only with a cancellation.

**The deadline is the database's.** `advance` expires a run past its deadline (120 seconds from admission, set by the row trigger) and refuses the move as `DEADLINE`, so a clock skew between the process and the database cannot extend a run; the process's own clock check is only a fast fail. `advance` also refuses `cancelled` (that is `cancel`, which raises the fence) and refuses `expired` before the deadline. The row trigger decides what a caller must not: an inserted run is `admitted`, at sequence 0 and fence 1, admitted now; an update that finishes a run stamps `finished_at` itself, so a back-dated finish cannot make a run deletable early. `mono_at` is the admitting process's monotonic time and means nothing in another process.

**A run that is never finished.** `agentic_explain_run_admit` is a lookup that also writes, by design: it expires an existing run past its deadline (the retry then replays the engine text, as for any finished run) before reporting on it. Because the row stays for the retention period, the key of an expired run is burned: a client that wants a new attempt uses a new idempotency key. The operator function `agentic_explain_run_sweep()` expires the rest, suspended organizations included; it skips rows a worker holds (`FOR UPDATE SKIP LOCKED`, in one order) so a busy run cannot fail it and two sweeps cannot deadlock. The store maps a lock timeout, a serialization failure or a deadlock to `RUN_STORE_BUSY`, which a caller may retry with the same key; the default isolation level is required.

**Who may read.** Runs are scoped to the requester as well as the organization: a run belongs to one person's request, and a colleague (an administrator included) cannot read, advance or cancel it. Receipts (0048) are scoped to the organization, because a receipt is the organization's record of its AI use. A support or audit reader across requesters, if one is wanted, is an operator function, not a capability-bound one.

**Retention.** The same rule as the receipts: a delete is refused, for every role, until a finished run is 2190 days old (6 years); an unfinished run is never deletable; both triggers are `ENABLE ALWAYS`; the operator purge `agentic_explain_run_purge(tenant or NULL)` is executable by no login. An organization may admit at most 1000 runs an hour (`RATE_LIMITED`, an initial value; the count is not locked, so concurrent admissions can overshoot it slightly, which is acceptable for an abuse cap). The same residuals as the receipts apply (the owner can disable or drop the triggers or the table; `DROP TABLE` fires no row trigger, so the down migration's `telesphoros.allow_runs_drop` refusal is the only guard against that; keep the table unpartitioned). Usage reservation and the fleet and tenant caps are the next slice.

## Foreign keys and their indexes

Some foreign keys have no index on their referencing columns (32 when this was last counted; `test/db/fk-indexes.pg-spec.ts` pins the condition, not the number). That is deliberate: PostgreSQL scans the child table for them only when a parent row is deleted or its key changes, and the application role holds no `DELETE` on any parent (the ledger, note and identifier tables also refuse deletes by trigger; reports and patients are soft-deleted). The queries that touch these columns read from the child to the parent by the parent's primary key, so the parent's index serves them. An index on the child would cost every insert and be read by nothing. The production audit (item 13) asked for five of them and was declined on this evidence (2026-10-24).

`test/db/fk-indexes.pg-spec.ts` pins the condition, not the list: a foreign key may go without a covering index only while the application role cannot delete from its parent. Giving the application role `DELETE` on a parent, or adding a key to a parent it can delete from, fails the test until the key is indexed. A hard delete by the owner role (a maintenance session) is not covered by it and would scan the child tables.

## Database alarms

Three CloudWatch alarms watch the instance itself (`database-alarms.tf`, into the audit topic): **free storage** under 4 GiB for three five-minute periods (no data counts as a breach), **CPU** averaging over 80% for three periods, and **connections** over 80 in one period. The numbers are judgements: nothing has run against this instance. Free storage near the ceiling means autoscaling (`db_max_allocated_storage`) is exhausted or data grows faster than the disk; high CPU, look for a runaway query or a deploy surge before resizing; high connections, count the tasks times their pool sizes (a deploy surge doubles the tasks for a few minutes) before raising the threshold or the instance class. The connection limit depends on the instance memory; the formula AWS documents for Aurora PostgreSQL is `DBInstanceClassMemory / 9531392`, and RDS PostgreSQL's row was not read. Written and never applied: no alarm exists in AWS yet.
