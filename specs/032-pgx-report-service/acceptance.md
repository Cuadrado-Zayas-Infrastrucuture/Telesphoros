# Synthetic acceptance specification

**Design only: none of the new cases below has been executed.** They define observable outcomes for future tests; they are not clinical dosing oracles. Use invented patients, laboratory IDs and report bytes. Generic rules use GENEA/GENEB as in existing fixtures. Cases mentioning real genes describe uncertainty/scope behavior; exact clinical expected cells require an independent qualified reviewer before implementation. Do not derive expected outputs from the code being tested.

Baseline B: authenticated synthetic laboratory; tenant T1/patient P1; final report R1 revision 1; exact PDF/JSON pair; manifest M1 with a tested and resolved GENEA finding F1; independent acceptance; context X1; reviewed synthetic rule K1 for drug D1; all prerequisites present. All artifacts remain synthetic and `clinicalUse=not-approved`, `actionable=false`. Baseline identifiers are scenario labels, not valid production DTOs.

## Required evidence by boundary

Import and authority cases require existing real PostgreSQL application-role/RLS and S3-emulator tiers, plus exact-version mismatch and transaction-failure controls. UI cases require real browser checks of chat upload, review dialog, source details and patient follow-up/reminders. Clinical source cases require independent pharmacist-authored expected cells and named review. FHIR requires profile/terminology validation; assays require laboratory analytical validation. A successful unit test cannot substitute for any of these.

Keep source fixtures separate from expected outcomes, and include mutation controls that remove a prerequisite, swap a patient, change a source version or suppress a limitation. Record test counts, skips, source versions, tool versions, checkout and reviewer. Existing reader-engine-absent skips remain explicit missing evidence.
