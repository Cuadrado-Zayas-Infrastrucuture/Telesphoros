# Identifier keys for drugs and genes (spec 039)

Date: 2026-11-12
Status: draft. `plan.md` is NOT approved; no code may be written until it is (constitution I). Decisions D1 to D9 are open. Two independent reviews are folded in: the first found 13 problems, one a blocker; the second confirmed 11 closed and 2 partly closed, and found 11 more, none a blocker, two of them decisions (D8, D9).

## Why

A drug in this system is a lower-case name and a gene is a symbol. Patient medications are stored by their RxNorm ingredient id (`patient_medications.drug_rxcui`), never by name. So the two cannot be joined, and nothing may join them by name: draft spec 031 (medication–gene review flags), requirement 3, asks for "the approved signed-knowledge RxCUI mapping contract" first, and forbids a case-insensitive name join as a shortcut.

Spec 033 (knowledge identifiers, K2, approved 2026-11-05) supplied the format half. A schema 1.3 guideline states its drug's RxNorm id (`rxcui`), a 1.3 gene map states its gene's HGNC id (`hgncId`), the engine copies both onto a result that has a citation when the guideline and every gene map it reads are 1.3, and migration 0071 stores them on `evaluation_results`. A result with no cell (a knowledge gap, a missing gene, no guideline) carries none, so the stored `drug_rxcui` does not find every result for a drug. Production already refuses any 1.2 file. Spec 033's own record says it supplied "the schema half of that contract only".

What is still missing, read at `ed9268a5`:

- The loader and the knowledge set key guidelines by drug name and gene maps by gene symbol, and never read the ids. Two files may give one drug two RxNorm ids, two drugs may share one, and two gene maps may share one HGNC id; all three load without a problem (`knowledge-loader.ts:91-96`, `knowledge-set.ts:33-39`).
- Nothing can answer "which guideline, if any, belongs to this RxNorm ingredient id?".

A data-migration audit of the business's AI plan, run for the founder on 2026-11-12, marked this HIGH: drugs keyed by name and genes by symbol in the knowledge and the stored results, with medications keyed by RxNorm id and no mapping between them.

## Scope

Invented data only. No real CPIC, RxNorm or HGNC content is fetched or written; `knowledge/cpic/` stays empty. No change to the knowledge format: `packages/cpic-schema` only exports a function that tells whether a value is an RxNorm id in either of its existing forms (`IDENTIFIER_FORMS`, private to `knowledge.ts`, stays private), so the mapping checks ids against the one definition and no consumer can alter it. No change to the engine, any stored result, migration, ledger hash, route, screen or clinical output. No caller is wired to the mapping in this slice: spec 031's flags still need their clinical signer, intended use and signed mappings, and nothing here supplies those.

| ID | Requirement |
| --- | --- |
| IK-1 | **One drug, one RxNorm id; one gene, one HGNC id.** When the loader builds a set, every schema 1.3 guideline for a drug must state the same `rxcui`, no two drugs may state the same `rxcui`, and no two gene maps may state the same `hgncId`. Each is a load problem in every mode, naming both files and the rule. |
| IK-2 | **No half-identified drug** (D4). A drug with both a 1.2 and a 1.3 guideline file in one set is a load problem in every mode: a lookup by id would see only part of it. A 1.3 guideline over a 1.2 gene map stays loadable, as today, and its results carry no identifiers (`identifiersFor`, spec 033 K2-6). |
| IK-3 | **Lookups by id.** The knowledge set answers, by exact string equality with no case folding, trimming or fallback to a name: the drug for an RxNorm id, the RxNorm id of a drug, the gene for an HGNC id, and the HGNC id of a gene. A drug or gene known only from 1.2 files has no id, and an id the set does not hold has no drug or gene. A set built directly, without the loader, that breaks IK-1 is refused when it is built, so the lookups never pick one of two answers. |
| IK-4 | **The medication mapping contract** (spec 031 requirement 3; D1). A pure function takes the knowledge set and a list of RxNorm ids, as plain strings, and returns one answer per id, in the order given: either `matched`, with the drug and each of its guideline files as its id and, when another file of the set supersedes it, that file's id; or `not-matched`, with a reason from a closed list: `no-identified-guideline` (no guideline in this set states that id) or `invalid-identifier` (in neither RxNorm form of spec 033 K2-5: digits, or `syn-rxcui-…`). It never matches by name: an id the set does not hold is `not-matched`, even when it is spelled exactly like a guideline's drug name. A repeated id gets the same answer each time it appears. `not-matched` means only that this set states no guideline for that id; it never means that no guidance exists (D6). |
| IK-5 | **A match is only as safe as the ids in the guidelines** (D2). The drug list holds ingredient (`IN`) and multiple-ingredient (`MIN`) RxNorm ids (`packages/shared-types/src/drug-list.ts:34`); a stored medication keeps the id and not its type. The mapping cannot tell them apart: it matches whatever id a guideline states. A combination product finds no guideline only because a guideline states an ingredient id. That is a curation rule, which nothing in this repository checks: a guideline states the RxNorm id of the drug its source names, which is a single ingredient except where the source's drug is itself a combination (D8), and never a salt, brand or product id. The clinical validation note records it, and the private curation registry is where it belongs. Splitting a combination product into its ingredients is a later spec. |
| IK-6 | **No caller yet; the medication boundary stands.** The mapping module imports only the knowledge set and the knowledge schema. In this slice nothing outside `services/knowledge` imports it or calls the four lookups of IK-3, and no file under `patient-medications/` imports anything from `services/`. A new spec enforces all three, reading `import`, `import type`, `export … from`, `require`, dynamic `import()` and a bare `import '…'`. Spec 029's boundary (`patient-medications/clinical-boundary.spec.ts`, MD-6) is unchanged and still passes. The spec that adds the first caller lifts the fence. |
| IK-7 | **Nothing that exists changes, except the test helper's ids.** The engine, every stored evaluation, the ledger and its hashes, every knowledge set id and every committed fixture stay byte-identical. The existing fixture sets are not edited; the conflict cases of IK-1 and IK-2 get new, test-only invented fixtures. One test helper changes: `toSchema13` in `apps/backend/test/helpers/knowledge.ts`, which gives every signed test copy one RxNorm id and one HGNC id, now gives each drug and each gene its own id, still beyond any range RxNorm or HGNC has assigned. Without it IK-1 would refuse every signed test copy. |
| IK-8 | **Problems carry no content.** A load problem names the files, the drug or gene where there is one, and the rule, as the loader's problems already do (`knowledge-loader.ts:95`); drug names and gene symbols are closed forms, not wording. The mapping returns ids and reasons only; it logs nothing. |
| IK-9 | **Deterministic.** The same set and the same list give the same answers, in the list's order, whatever order the files were read in. |

## Decisions

| # | Decision | Options | Recommendation | State |
| --- | --- | --- | --- | --- |
| D1 | Where the mapping lives | (a) A pure module in `services/knowledge`, taking RxNorm ids as plain strings, so neither side imports the other. (b) In the medications module, which breaks spec 029's MD-6 boundary. (c) In `packages/shared-types` | (a). The same way the intelligence plan passes medicines to the engine: as plain values | Open |
| D2 | Multiple-ingredient medications | (a) Not split in this slice; the mapping matches only the id a guideline states, and the curation rule of IK-5 keeps those to single ingredients. (b) Split them into ingredients now | (a). Splitting needs RxNorm relationship data, its licence reading and a reviewed table | Open |
| D3 | HGNC ids on stored gene states (`evaluation_gene_states`, symbol only today) | (a) Not in this slice. (b) A new migration now, ids stored when known, hashed only when present (as spec 033 K2-8) | (a). Every identified result already stores the HGNC id of each gene behind it (0071), the knowledge set can answer symbol to id (IK-3), and a public migration now would take number 0075, which the private repository already uses, forcing a renumbering at the next merge from public | Open |
| D4 | A drug with both 1.2 and 1.3 files in one set | (a) A load problem (IK-2). (b) Load it and treat the drug as unidentified | (a). A half-identified drug would let a lookup by id silently miss guidelines. Production already refuses 1.2, so this changes nothing there | Open |
| D5 | Asking the engine for drugs by RxNorm id | (a) Not in this slice: a caller maps ids to drugs with IK-4 and asks the engine by name, as today. (b) Add an id option to the engine's request now | (a). The engine and its request schema stay unchanged, and so do the schemas the private repository builds from them | Open |
| D6 | The RxNorm release | A medication records the drug list's RxNorm release; a guideline records none. An id RxNorm has since retired or remapped finds no guideline, and that silence reads like "no guideline". (a) Now: IK-4 says `not-matched` never means "no guidance exists", and the clinical note says why; a guideline's RxNorm release is recorded with the first real content (intelligence plan phase 4). (b) Add an RxNorm release to the knowledge format now | (a). A format change belongs with the first real content, and this slice has no caller to mislead | Open |
| D7 | Who approves the mapping contract | Spec 031 asks for an approved contract and, before its own code, a named clinical signer. (a) The founder's approval of this plan approves the mechanism only; approving it for clinical use stays with spec 031's named signer, before any caller. (b) Name the clinical signer now | (a). This slice decides no clinical question and shows nothing to a clinician | Open |
| D8 | A source drug that is itself a combination | The bundled drug list, from CPIC's drug records, gives two CPIC drugs only as multiple-ingredient (`MIN`) ids: sulfamethoxazole / trimethoprim (10831) and fluticasone / salmeterol (284635) (`packages/shared-types/src/drug-list/bundled.json`). (a) A guideline states the id its source's drug record gives, the combination's id where the source's drug is a combination, so a medication of that combination matches it, and one of either ingredient alone does not (IK-5). (b) Guidelines state single ingredients only, so these two never match. (c) Pass each medication's RxNorm term type into the mapping and return a third reason for a combination | (a). It follows the source, needs no new input, and the clinical note names both drugs | Open |
| D9 | A pharmacogenomic locus that is not a gene | Schema 1.3 requires an HGNC id on every gene map (spec 033, `knowledge.ts:240`), and some CPIC loci have none (for example the CYP2C cluster variant in the warfarin guideline). Under IK-1, borrowing a neighbouring gene's id is refused. (a) Not settled here: such a locus cannot be a 1.3 gene map until a format decision says how it is identified, made with the first real content that needs one. (b) Decide its identifier now | (a). It is a format question for real content, and no invented fixture needs it | Open |

## Done when

1. Each conflict case of IK-1 and IK-2 has an invented fixture the loader refuses with the named rule, and removing the rule turns a named test red.
2. The lookups of IK-3 and the mapping of IK-4 give hand-written expected answers on invented knowledge and an invented list of ids, among them: an id spelled exactly like a guideline's drug name (`no-identified-guideline`, which catches any fallback to a name), an id of a drug known only from a 1.2 file, a malformed id, a repeated id, and a drug with a superseded file. The answers are written before the code.
3. Every existing suite passes, unchanged except for the test helper of IK-7, including the pinned fixture hashes and knowledge set ids, the engine and the MD-6 boundary.
4. A clinical validation note in `docs/clinical-validation/` records what the mapping does and does not decide, the curation rule of IK-5, and the meaning of `not-matched` (D6) (constitution IV).

## Not in this spec

- Any medication–gene flag, route, screen or clinical output: spec 031, which still needs its clinical signer.
- Real RxNorm or HGNC content, a drug list change, or a guideline for a combination product (D2).
- HGNC ids on stored gene states (D3) and asking the engine by id (D5).
- The two stale patterns in spec 029's MD-6 boundary spec (`services/engine` and `services/interpreter` match no folder; the real ones are `recommendation-engine` and `ai-interpreter`), found while writing this spec. IK-6's new spec is the first fence in that direction; fixing MD-6 is a follow-up.
- The offline report lookup's sertraline routing (`report-lookup/routing.ts:23`, `:67`), which names its drug and is reached only by specs.
- The private repository. Its curation registry already requires both ids on every drug and gene record and compiles them into 1.3 files. It takes this change when public is next merged into it, and that merge runs the private repository's whole loop again, as its rules require: any private test or set that shares an id across drugs or genes, or mixes 1.2 and 1.3 files of one drug, will fail there and be fixed there.

## Not checked

- Which existing tests IK-1 and IK-2 would refuse, beyond the signed test copies of IK-7, and whether any test pins the content hash of a signed test copy, which the helper change of IK-7 alters. The first task checks both before anything depends on them. The first review found no test that mixes 1.2 and 1.3 guidelines of one drug.
- How the front end, the FHIR pilot package and the stored-result readers use drug names. None of them is changed here; the study for this spec read them by search only.
